## 1. 问题：设计评审被激励成"实现规格无限求精"

多模型 AI 评审有一个结构性副作用：**每个模型都想找到别人没找到的问题**。
当设计稿已无架构级缺陷时，模型会把注意力转向实现细节（对象布局、编码
大小写、每个失败路径），而这些细节按原指南会被定级 P2 → "A 不得挂必修
项" → 只能给 C → 再开一版设计 → 全模型重新评审。一条实现合同缺口的
默认代价 = **新设计版 × 四模型**。

本项目五轮 OTA 评审的实际数据：

| 轮 | 挡住的问题 | 性质 | 该挡吗 |
|---|---|---|---|
| v1→v2 | TLS 继承 Trust 开关；清单无签名；框架在 setup 前自动自证 | 协议/架构 P1 | ✅ |
| v2→v3 | 8s WDT < 实测 setup 阻塞 8.4s（健康镜像必被误回滚） | 协议/架构 P1 | ✅ |
| v3→v4 | 签名对象把 `sig` 编进待签输入（数学上不可构造） | 协议/架构 P1 | ✅ |
| v4→v5 | TWDT 句柄写法；取号 API 副作用写入比较式 | 协议/架构 P1 | ✅ |
| v5→v6 | 队列谁 drain；manifest 是 POD 还是指针；hex 大小写 | **实现合同** | ❌ 过度 |

前四轮的 P1 是真雷（按正文编码必变砖/必验签失败）；第五轮的"发现"全部
是"补一段与仓库既有模块同构的约定即可"的合同缺口。**两类问题在同一套
定级表里没有分轨**，是空转的制度根因。

## 2. 解法：三条分轨 + 四个机制（§2.5 核心）

### 2.1 三类发现，先分类再定级

| 类 | 判定 | 挡 L1？ | 开新版？ |
|---|---|---|---|
| 协议/架构不可满足 | **最小修复必须改承重规范**（否则合法输入全失败/健康设备变砖） | 是 P0/P1 | 是 |
| 实现合同缺口 | 最小修复 = 补一段**与仓库既有模块同构**的约定 | 否 P2@L2 | **否** |
| 完备性/文风 | 注释、样本、矩阵格子 | 否 P3/Nit | **否** |

判定锚是**最小修复**而非 reviewer 的严重感。"这个决定在仓库里是否已有
一份验证过的现成答案"是可核实的事实问题。

**负面清单**（防"实现合同"被当垃圾桶）：最小修复触及签名/回滚/密钥/
TLS/变砖路径之一 → 强制协议类，不得以"存在可行实现"豁免。

**条件式反假想级联**：禁止以"未来实现者可能写错"作多跳灾难推演（封顶
P3）；但"设计的缺失使**任何**实现都无法满足正文声明"仍报 P0/P1——用
可核实的条件取代不可核实的假设。

### 2.2 设计稿的 A ≠ 代码的 A

无协议/架构 P0/P1 时**必须给 L1+A**（可附实现合同清单绑 L2/G-合入）；
因"还可以更完整"给 C = 违规。C 的 required action 必须是"改哪一节规范"，
不得是"把实现细节写完整"。实现合同用**跟踪表**（ID/目标/绑定 commit/
L2 证据/合入状态）承接，防开工后消失。

### 2.3 复审默认 delta + 三个扩面通道

只核本版 diff + 变化点；未改章节当已闭合。扩面仅限：①修复引入回归；
②新旧段直接矛盾；③**拿出了独立的带反例 P0/P1 证据**（"此前没检查过"
不是理由，证据才是）。

### 2.4 轮次与多方

一轮无协议/架构 P0/P1 → 属主冻结设计，下一对象是实现 commit。收口轮
默认一名 reviewer 做 delta——**但任一 reviewer 拿出带反例的 P0/P1 立即
回多方轮**。同主题满 3 轮 → 触发**属主裁决**（裁决仍看内容，不自动放行）。

## 3. 被拒绝的方案（及可证伪的反例）——这部分最值得参考

四个"看起来能提速"的机制被三方一致或多数拒绝，每个都有**来自本项目真实
评审史的反例**：

### ① 主审制（旁审无独立阻断权）
- **吸引点**：消除"4 模型任一否决"的军备竞赛。
- **反例**：OTA v4 的签名自指 P1 由三家命中、一家（qwen）漏审——若漏审
  者恰好是主审、其余旁审无阻断权，这个"合法清单不可构造"的 P1 就随 A
  开工流入实现了。五轮评审史核对：**没有任何模型包揽全部真发现**。
- **正确解**：阻断力按**证据严重级**分配（任何 reviewer 的协议/架构
  P0/P1 均阻断），而非按身份分配。军备竞赛的解药是"严重级纪律+delta
  锁定+轮次熔断"，不是"取消旁审资格"。

### ② 静默表对文档一律禁用
- **吸引点**：文档没有运行日志，不该因载体被上调定级。
- **反例**：manifest 所有权那条真 P1 就是静默的（按字节复制入队 → 悬空
  指针 → 无差异化报错）。"DOC 一律有声表"会把它机械降到 P2。
- **正确解**：禁的是"假设未来实现错误"的假想级联上调；"设计正文已唯一
  确定的必错后果"无论载体都是 P0/P1。按后果分，不按载体分。

### ③ 轮次硬顶自动 A-
- **吸引点**：强制止损。
- **反例**：签名自指恰好在**第 4 轮**才被四方共同发现——硬顶 3 轮自动
  放行会在真 P1 未闭合时开工。
- **正确解**：轮次触发**属主裁决**（内容触发），不自动降门槛。

### ④ 通用四态审批（A-）
- **吸引点**：给"带跟踪项接受"一个名字。
- **问题**：稀释代码评审"A 不挂必修项"的既有语义。
- **正确解**：设计稿专用"L1+A + 实现合同表"表达同一语义，代码侧
  A/B/C 零改动。

## 4. 迁移到其他项目的检查清单

1. 你的项目是否区分**设计评审**与**代码评审**的结论语义？（不分 = 实现细节
   会倒逼设计版）
2. 设计稿发现是否有"先分类再定级"的轨道？（协议不可满足 / 实现合同 /
   完备性）
3. 判定锚是否可核实？（"最小修复改不改承重规范"优于"reviewer 觉得严重"）
4. 实现合同有没有**防丢失机制**（跟踪表 + 绑定实现 commit）？
5. 复审是否默认 delta？"未改章节"有没有被当新架构重开？
6. 多模型评审的阻断权是否绑定**证据严重级**而非模型身份/票数？
7. 有没有轮次兜底？它触发的是**属主裁决**还是自动放行？
8. 被拒绝的提速方案是否留下了**可证伪反例**的书面记录？（否则半年后会
   有人再提一遍）
