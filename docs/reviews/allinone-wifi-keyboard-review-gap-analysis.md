# allinone WiFi/键盘设计评审漏检分析

- **分析日期**：2026-08-16
- **分析对象**：[allinone-design-review-request.md](../allinone-design-review-request.md)、[allinone-design-review-result.md](../allinone-design-review-result.md)
- **历史基线**：commit `27ad8d5`

## 1. 结论

早期评审并非缺少可用线索，而是把“移除触摸后能否用键盘操作 dropdown”这一项狭窄整改，误当成了“WiFi 配置交互完整且可靠”的结论。

`allinone-design-review-result.md` 将“WiFi 键盘选择”标为通过，只证明设计中存在 `keypad` 读取和关闭 dropdown 的路径；它没有验证 SSID 输入能力、扫描和连接的阻塞行为、保存时机、键盘事件积压、页面生命周期及错误恢复。由于 allinone 尚未实现且目标硬件未连接，该项当时更合理的结论应是 **“设计不通过”或“缺少证据”**，而不是“通过”。

## 2. 当时已有证据、应当发现的问题

| 设计证据（`27ad8d5`） | 当时应识别的风险 | 后续表现 |
|---|---|---|
| SSID 固定为扫描结果 `lv_dropdown` | 隐藏 SSID、暂未广播或扫描漏掉的 SSID 无法手动输入 | 后续改为可编辑 textarea 和扫描选择双模式 |
| Enter 直接执行 `WiFi.scanNetworks()` | 同步扫描会阻塞 UI 主循环，无法持续消费键盘事件，也没有取消、超时和页面退出契约 | 后续多轮修复异步扫描、覆盖层、超时及回调生命周期 |
| `+`/`-` 被定义为候选导航键 | 一旦补充手动 SSID 输入，合法字符与导航命令必然冲突，设计缺少显式模式区分 | 后续引入编辑模式/扫描选择模式 |
| 密码 Enter 后先 `putString()`，再 `WiFi.begin()` | 认证失败、SSID 不存在或超时时会把无效凭据持久化，并覆盖旧的可用配置 | 后续改为连接成功才保存 |
| 全局读取模型为 `keypad_get_val()` + `keypad_set_flag()` | 单字符槽位没有积压队列、溢出策略和页面切换边界；阻塞期间多个按键只能覆盖或残留 | 后续引入软件 FIFO，又继续暴露跨页面残留和硬件 FIFO 问题 |
| 只描述扫描成功后的 dropdown 操作 | 缺少扫描启动失败、零结果、超时、取消、迟到结果、离开页面及重扫代次的状态定义 | 后续每一轮分别补齐并暴露竞态 |
| 只描述“保存 + 连接” | 缺少明确的 Connect、Clear、失败反馈和旧配置保留语义 | 后续按真机反馈重构 |

这些问题不依赖 HD-V2 真机布局，单靠设计稿和当时的 `peri_keypad.cpp` 就能够发现。

## 3. 当时难以发现或不属于早期漏检的问题

### 3.1 依赖后续真机证据

- HD-V2 实际具有 Alt、双 Shift、Mic 和音量键，且物理矩阵坐标与旧假设不同。
- 触摸焦点变化后，LVGL 焦点与内部 `wifi_cfg_field` 状态不同步。

当时申请书明确说明目标硬件未连接，因此这些问题可以记为风险或缺少证据，不能要求评审准确推导全部物理布局。

### 3.2 后续整改新引入

- 软件字符 FIFO 的覆盖、跨页面残留及清理边界。
- `esp_wifi_scan_stop()`、`scanDelete()` 与异步 `SCAN_DONE` 回调竞态。
- 扫描完成覆盖用户已修改的草稿。
- 扫描覆盖层、结果横幅及 placeholder 的具体实现错误。
- WiFi Test 使用错误端点、断网无反馈和同步请求冻结 UI。

这些代码或交互在 `27ad8d5` 时尚不存在，不能归为早期评审漏检；但它们说明后续复审仍需开放式检查，不能只验证上一轮修订项。

### 3.3 后续新增或明确化的产品需求

- Alt 作为临时符号层、双 Shift 行为。
- Save 改为 Connect，连接成功才保存。
- 扫描倒计时、结果横幅、Clear 按钮。
- WiFi Test 入口及其最终位置。

新增需求本身不是历史缺陷，但其中“连接失败不得覆盖旧凭据”等数据安全语义，本应在原设计评审时主动提出。

## 4. 漏检的过程原因

### 4.1 评审范围被申请书的九项整改锚定

申请书把本次工作定义为对九项既有 Finding 的集中整改，其中 WiFi 项仅是“移除触摸后 dropdown 点击事件不会触发”。评审随后也只回答了这个预设问题，没有把 WiFi 配置作为独立状态机重新审计。

### 4.2 通过标准过窄且证据标准不一致

结果用“当前设计使用 keypad 读取和关闭 dropdown”判定通过，实际只验证了代码路径存在，没有验证：

- 任意合法 SSID 是否可表达；
- 快速连续输入是否不丢失；
- 扫描、连接和 HTTP 阻塞期间 UI 是否仍可响应；
- 失败后 NVS、草稿和页面状态是否保持一致；
- 页面退出、取消和迟到回调是否安全。

同一份结果对 allinone 完整构建和真机功能标记“缺少证据”，却对同样尚未实现、尚未真机验证的 WiFi 交互标记“通过”，结论门槛不一致。

### 4.3 集中评审造成注意力稀释

一次提交同时包含 TLS、GPS 并发、EPD 刷新、UTF-8、菜单结构和 WiFi 交互。CA 损坏、HTTPS 时间前提等高风险问题占据了主要审查预算，WiFi 项被当作低复杂度的输入替换处理，没有展开完整交互链。

### 4.4 没有使用状态机和事件序列评审

评审按文件和既有 Finding 检查，没有枚举下列关键序列：

- 输入 → 扫描 → 输入 → 迟到结果；
- 扫描中退出 → 回调完成；
- 连接中连续按键 → 进入下一页面；
- 连接失败 → 重启 → 自动连接；
- 触摸切字段 → 键盘继续输入；
- 页面 A 留有按键 → 页面 B 激活。

后续多轮问题大多正是这些跨状态、跨异步边界序列。

### 4.5 过度接受申请书中的实现声明

申请书把“纯 keypad 驱动”“大写 SSID 可正常输入”“显示失败原因”等描述当成已成立事实。评审没有反向检查其前提，例如 dropdown 根本不能手动输入 SSID、单字符交付模型无法承诺连续输入可靠性、先保存后连接会污染持久化状态。

## 5. 改进措施

1. **设计与代码分轮评审**：先冻结交互状态机、数据持久化和生命周期契约，再评实现；避免十余个跨领域改动集中申请。
2. **每个输入功能必须提交状态表**：列出状态、事件、守卫、动作、退出清理、异步完成处理和错误恢复。
3. **强制负向场景清单**：至少覆盖零结果、超时、取消、快速连续输入、页面切换、迟到回调、重启和旧数据保留。
4. **硬件证据门槛**：按键矩阵、修饰键和触摸焦点未经目标硬件验证时，只能标“缺少证据”，不得标“通过”。
5. **事件交付模型单独评审**：明确硬件 FIFO、软件 FIFO、容量、溢出、清空时机和页面归属；任何同步阻塞调用都要分析事件积压。
6. **持久化采用提交语义**：先验证临时配置，成功后原子替换旧配置；失败不得破坏已知可用状态。
7. **复审保持开放式检查**：除验证上一轮 Finding 外，必须检查修复引入的新状态、新资源和新生命周期。

## 6. 对早期结果的修正

`allinone-design-review-result.md` 中：

> WiFi 键盘选择：通过

应修正为：

> **WiFi 配置交互：不通过。** keypad 可以替代触摸操作 dropdown，但设计无法手动输入未扫描到的 SSID；同步扫描和连接缺少事件积压、取消及页面生命周期设计；失败凭据会先写入 NVS。目标硬件未连接，修饰键矩阵和完整输入可靠性另记为缺少证据。
