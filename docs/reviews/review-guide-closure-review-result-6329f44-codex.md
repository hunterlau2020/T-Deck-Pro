## Findings

### P2：Grok 的 delta 规则没有为新证据的既有 P0/P1 留出扩面通道

- **位置**：[Grok 提案 §4.7，拟 §2.5.3](review-guide-closure-review-request-6329f44.md)
- **证据**：提案仅允许“修复引入回归”或“新段与未改段直接矛盾”时扩面，并称未改段
  已闭合。若后来发现独立、可复现的 P0/P1 证据恰好位于未改段，既不属于该两类，
  又会被“不得以我还没核过那一节扩面”排除。
- **影响**：为了压缩复审范围，可能压掉真正的协议/架构阻断项；这是设计稿收口的错误
  安全边界。
- **最小修复**：delta 仍为默认，但第三个扩面理由必须是“有独立的 P0/P1 证据”，并在
  结果头部注明证据与段落；“此前没检查”本身仍不是理由。

### P2：两份提案都须把“实现合同”的可追踪交付定义完整

- **位置**：[Grok 提案 §4.7，拟 §2.5.1/§2.5.2](review-guide-closure-review-request-6329f44.md)，
  [Claude 提案增补 1/3](review-guide-v1.3-review-request-6329f44.md)
- **证据**：Grok 正确地将 POD/指针、drain 点等移到实现合同，但只笼统要求绑定
  L2/G-合入；Claude 的 `[Implementation Note]` 更明确规定不得作为阻断，却没有规定
  必须由哪一份实现申请逐项验收。两者都可能使合同在设计 A 后消失。
- **影响**：把设计阶段的过度阻断改成实现阶段的遗漏，不能形成可靠的快迭代闭环。
- **最小修复**：结果模板增加“实现合同”表：`合同 ID / 正确性目标 / 绑定实现 commit
  或申请 / L2 验证证据 / G-合入状态`。只有存在至少一种可行的、与既有契约相容的
  实现时，未定布局才可归此类；否则仍是协议/架构缺陷。

### P2：Claude 的三轮后自动 A- 会以轮次取代安全事实

- **位置**：[Claude 提案增补 4](review-guide-v1.3-review-request-6329f44.md)
- **证据**：达到三轮并不证明未闭合 P0/P1 已消失；本项目 OTA 签名对象自指即是在后期
  才成为明确的架构问题。轮次只能触发属主裁决，不能自动降低阻断门槛。
- **影响**：可能将仍有实证的协议/架构缺陷放行开工。
- **最小修复**：改为“第三轮触发属主收口裁决”；裁决仍以是否存在未闭合协议/架构
  P0/P1 为条件，而不是自动 A-。

### P2：Claude 的主审一票制和 DOC 静默表禁用过宽

- **位置**：[Claude 提案触发问题 2/5、增补 2](review-guide-v1.3-review-request-6329f44.md)
- **证据**：主审制会让旁审发现的、带可复现证据的 P0/P1 失去独立阻断效力，违背现行
  “证据 > 票数”。“DOC 一律查有声表”则把文档中唯一指定、但会静默破坏安全控制的
  不可满足约束，按载体而非实际后果降级。
- **影响**：前者增加模型盲点造成的漏审风险，后者机械弱化真实架构缺陷。
- **最小修复**：采用“首轮/疑似 P0/P1/属主点名才多方”的触发机制，而非主审否决权；
  用“是否存在可行的正确实现”区分实现合同与架构缺陷，而不是按 DOC/CODE 机械切换
  有声表。

### P3：Claude 新增 A- 会与既有代码 A/B/C 和 G-合入语义重叠

- **位置**：[Claude 提案增补 3](review-guide-v1.3-review-request-6329f44.md)
- **证据**：现行 G-合入只定义 A 与 C 的后果。新增 A- 若同时适用于代码和设计稿，会
  使“可直接合入”与“尚有 P2 跟踪项”之间的门禁责任不清。
- **最小修复**：不新增第四种通用审批态；设计稿使用明确的 `L1+A（开工接受）`，并以
  上述实现合同表承接 P2/P3；代码继续使用原 A/B/C。

## 已通过项

- 两份提案正确指出：设计 L1 不应把伪代码当作生产 C++ 的 ABI、对象布局或析构规则
  逐项验收；只要已有可行、合约相容的实现选择，这类问题应在 L2 核。
- Grok 的三类发现和“实现合同不倒逼设计 vN+1”是小步迭代的合适骨架。
- Claude 的“复审锁定 diff + 直接波及上下文”方向正确；需要上述 P0/P1 证据例外。
- 两份提案都保留了签名自指、必然误回滚、变砖、泄密等真正架构问题的阻断原则，
  该底线应保持。

## 建议的合并规则

1. 设计稿按“协议/架构不可满足、实现合同、完备性”三类处理；仅第一类阻断 L1。
2. 无第一类问题时给 `L1+A`，实现合同必须带 ID 并绑定下一实现申请的 L2/G-合入。
3. 设计复审默认 delta；仅回归、直接矛盾、或带独立证据的既有 P0/P1 可扩面。
4. 收口轮默认一名 reviewer；首轮、疑似 P0/P1、属主点名时再多方评审。轮次达到三轮
   只触发属主裁决，不自动放行。
5. 代码评审的 A/B/C、静默定级表和“证据 > 票数”维持不变。

## 对称三格

1. **范围**：逐段核对两份提案的触发问题、拟文和现行 v1.2 的 L1、门禁、定级、
   结果模板与修订流程。
2. **反例**：以“后续出现有证据的既有 P0/P1”检验 delta 锁定，以“实现合同没有后续
   绑定”检验开工放行，以“第三轮仍有架构证据”检验自动 A-；三者均能击穿无条件规则。
3. **未做的验证**：纯文档规则，无 BUILD/HW；未修改 `docs/review_guide.md`，因此不对
   任一落地文本作编译或真机声明。
