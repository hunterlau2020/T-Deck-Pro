## Findings

### P1：waitbox Close 不能被定义为非幂等 POST 的“取消”

- **位置**：`docs/penpal-design.md` §3.2（waitbox Close）、§2 ③/⑤/⑥/⑧。
- **证据**：设计将所有网络请求的 Close 定义为 `s_pp_gen++`、`busy=false`、任务不杀；结果只会因代次不匹配而在 UI 侧丢弃。发信、纠错、润色和建议端点包含 POST，其中发信会产生服务端副作用。关闭 waitbox 后，该 HTTP 请求仍可能成功完成；UI 已解除 busy，用户可重试发信，造成重复信件。
- **影响**：UI 显示“取消”却不能撤销已经发出的写操作，重试可产生重复副作用。
- **最小修复**：对可产生副作用的请求使用服务端幂等请求 ID，或实现可中止的传输并在允许重试前等待任务退出；否则将 Close 明确为“后台继续/不再等待”，并禁止立即重试同一写操作，不能称为取消。

### P2：主题按字符限制，但存储按不足的字节缓冲，会破坏线程查询键

- **位置**：`docs/penpal-design.md` §4.2、§5。
- **证据**：COMPOSE 允许 Title 最多 60 个字符，但 `pp_thread_row_t::subject[64]` 只能容纳 63 个字节加终止符。UTF-8 输入中 60 个字符可远超 63 字节；服务端返回的主题也没有已记录的 63 字节上限。该字段还是读取线程的查询 subject 和回复主题的来源。
- **影响**：截断后可能无法按原主题获取线程、错误聚合，或生成错误的 `Re:` 主题。
- **最小修复**：保存完整、用于 API 的 canonical subject（建议 `std::string` 或明确足够大的字节上限），显示层再做 UTF-8 边界安全截断；输入限制也应按 UTF-8 字节或服务端合同统一定义。
