## 复核方法

v4 的核心卖点是"废除拍脑袋 8s，改为先校准后定值 + 具名喂狗 + EPD 首帧
门控自证点"，逐条处置了 v3 三方收敛的 P1 与另外 7 P2/5 P3。这类"这轮
专门修上一轮最大的洞"的稿子，最容易犯的错是**修复本身引入新的、同等
严重的洞**——所以本轮重点不是重新验证 v3 已经查过的"A7682E_init 6.1s"
之类事实（那些结论未变，仍然成立，不再重复举证），而是**逐字审查 v4
新写的每一段规范性文字是否真的自洽、可执行**。

## Findings

### P1：清单签名对象把 `sig` 自身列进被签名字段，构成不可解的自指

- **位置**：`docs/ota-update-design.md` §2.1（"**签名对象** = 七字段按序
  拼接的规范化字节串...`sig` = ECDSA P-256/SHA-256...七字段全必填"）。
- **证据**：清单 JSON（§2.1 代码块）恰好七个键：`version/url/size/
  sha256/seq/notes/sig`。正文明确定义"签名对象 = **七字段**按序拼接"，
  随后又定义 `sig` 本身就是对这个"签名对象"的 ECDSA 签名——即
  `sig = Sign(concat(version, url, size, sha256, seq, notes, sig))`。
  等式右边含 `sig`，左边也是 `sig`：发布脚本要算出最终 `sig` 之前必须
  先知道 `sig`，无法构造。这不是"实现时小心点"的问题，是**数学上不可
  满足**的规范——按字面实现，发布脚本要么放一个占位 `sig` 签名（设备
  端拿到真实 `sig` 后重新拼出的字节串必然不同，验签必然失败），要么
  开发者凭经验"知道该排除 sig"而悄悄不照做，文档与实现从第一次发布就
  分叉。
  - **这是 v3→v4 的一次真实回归**：v3 §2.1 对同一签名对象给的是**显式
    枚举的六个具名字段**——`version \n url \n size(十进制) \n sha256 \n
    seq(十进制) \n notes \n`，字面上就没有 `sig`，是自洽、可执行的。
    v4 为了加入"notes 不含 `\n`/`\r`"和"JSON 值直接拼接 vs 按行切分
    JSON 文本"这两条新澄清（都对，是本轮的正确改进），把原本显式的
    六字段枚举**换成了一句"七字段按序拼接"**，在措辞上从"哪几个字段"
    的确定枚举退化成"数一数 JSON 有几个键"，顺带把 `sig` 计入了进去。
    是一次表达方式的退化，不是全新设计缺陷——但影响与 Codex 本轮判定
    一致：任何人照着 v4 现在的文字去写发布脚本或设备端验签，都会先撞
    上这个自指再发现问题。
- **影响**：后果 **B**（协议/契约不可满足——不是运行期偶发失败，是
  协议本身无法被正确实现）；可达性 **1**（第一次真正按文档实现签名/
  验签即触发，不需要任何特殊条件）；有声（验签失败会报错，不是静默
  漏洞，但要到实现期才会被发现，此时已经绕了一圈）。坐标
  **B/1/有声 → P1**（与本轮 Codex 判定一致）。
- **两轴**：验证状态 `VERIFIED`（DOC：字段表 + 签名定义两处原文直接
  推出矛盾，不依赖任何环境/设备）；契约符合性 `VIOLATES`（v4 §9 自身
  "字段/键名一致性"这条文档对齐要求——"签名对象"这个术语的外延和
  "七字段 JSON"的外延被文档自己混用成了同一件事）。
- **最小修复**：把 §2.1 的"签名对象"定义改回 v3 式的**显式六字段
  枚举**（`version, url, size, sha256, seq, notes`，明确排除 `sig`），
  同时保留 v4 本轮两条真正的改进（"取 JSON 值直接拼接不按行切分"、
  "notes 禁止 `\n`/`\r`"）——两者不冲突，只是需要在同一段话里说清楚
  "七个 JSON 键，其中六个进签名字节串，`sig` 是签名结果本身、不参与
  自签"。同批在 §8.3 加一条用例："发布脚本对占位/错误 `sig` 之外的
  六字段正确签名 → 设备验签通过"，把这条规范性文字的可执行性钉死成
  测试用例，防止再次退化。

## 已通过项（本轮独立复核，非转述）

- **`ui_disp_full_refr_seq()`/`ui_disp_flush_done_seq()` 首帧门控**
  （Codex P1-A 的修复）：独立核查 `ui_deckpro_port.h:42-43` 声明、
  `ui_deckpro_port.cpp:42-50` 的实现——两个 `ui_` 前缀包装函数分别
  转调 `factory.ino:864` 的 `disp_full_refr_seq()` 与 `:871` 的
  `disp_flush_seq_done()`，且这套"取号→轮询比较"模式**已经在生产代码
  里被两处消费**（`ui_deckpro.cpp:2808/2830` 的 WiFi 扫描覆盖层、
  `:4494/4518` 的 Sleep 倒计时）。v4 把自证门控接到这套已验证过的既有
  机制上，而不是发明新东西，风险很低，核实无误。
- **`CONFIG_ESP_TASK_WDT_PANIC=y` 补证**（我自己 v3 轮 P2 的直接回应）：
  v4 §1/§5.2/§7.3 三处都点了这个宏名并入基线复核清单，且把"8 秒内
  WDT 复位"的措辞改成了"预期...（§8.1a 待验证）"——正是我上一轮要求
  的"不要把推理写成已核实事实"，采纳到位。
- **校准优先于定值**（我自己 v3 轮另一条 P2 的回应，且做得比我原本
  建议的更彻底）：不再是"验证 8s 是否够用"，而是从设计层面直接**废除
  拍脑袋数字**，改成"先在两台真机各打点、再拿实测值定 T（×2、下限
  30s）"，把校准列为实施顺序 §9 的第 0 步——这是比"多留安全边际"更
  正确的方法论，不再依赖任何未经验证的假设。
- **硬件锁并发回归用例补齐**（我自己 v3 轮 P3 的回应）：§8 第 3 条
  "下载中途 Back 离屏→重进→立即 Update→第二请求被拒绝"，与我上一轮
  指出"Codex P1-A 最高定级的修复缺专属用例"完全对应，已补齐。
- **`seq` 提交时机改到 `Update.end(true)` 之后**：核对 §2.1 新文字与
  v3 时的旧逻辑对比，确认"Check 阶段只比较、下载成功后才写 NVS"能
  正确消除 Grok/Qwen v3 轮给出的"下载失败后同版本无法重试"反例。
- **签名编码 65B 未压缩 SEC1 单一格式**：与 SEC1 规范核对（压缩点
  33B、未压缩 65B、无前缀仿射 64B 三选一取未压缩，且显式禁止另外
  两种），术语和字节数上自洽，修正了 v3"65B 压缩点"的自相矛盾表述。

## 存疑但不阻断（建议随实现一并处理，不构成本轮退回理由）

- **`esp_task_wdt_add(loopTask)` 的参数写法值得商榷**：`loopTask` 在
  Arduino-ESP32 的 `main.cpp` 里是任务入口**函数**，不是
  `TaskHandle_t`；`setup()`/`loop()` 本身就跑在 loopTask 上，所以更
  稳妥、不依赖具体核心版本是否导出任务句柄符号的写法是
  `esp_task_wdt_add(NULL)`（NULL 表示"当前调用任务"，这是 ESP-IDF
  API 的标准用法，与框架内部具体怎么命名句柄变量无关）。本环境无
  框架源码缓存，无法确认该版本是否确实导出了可用的任务句柄符号，
  所以不定性判断谁对谁错，但建议 §5.2 直接把示例代码改成
  `esp_task_wdt_add(NULL)`/`esp_task_wdt_delete(NULL)`，从写法上绕开
  这个疑问，比纠结句柄名字更省事。
- **"函数内部具名喂狗点"如果改的是共享代码路径（如 EPD `nextPage`/
  BUSY 等待循环），需要说明这些 `esp_task_wdt_reset()` 调用是否要用
  "当前是否仍在预自证窗口内"这样的条件守卫**：EPD 刷新在自证之后的
  正常运行期间也会持续发生，若喂狗调用不加区分地留在共享代码里，
  自证后 `esp_task_wdt_delete()` 退订了 loopTask，之后每次正常 EPD
  刷新再调到同一处 `esp_task_wdt_reset()` 会因未订阅而返回错误码——
  不是崩溃，但是一个需要显式处理（忽略返回值或加守卫）的分支，
  §5.2/§10 目前没有点出这一点。建议实现合同清单里补一句。
- **两机各测一次的校准数据不构成所有场景的上界**：GPS 冷启动重试、
  SD 卡读写偶发变慢等路径在"某一次正常开机"里不一定被打点样本覆盖到；
  ×2 安全边际能吸收一部分方差，但不是"覆盖所有已知会更慢的路径"的
  证明。建议校准步骤里至少包含一次刻意触发 GPS 冷启动重试路径的打点
  样本，而不是只测"最常见的一次开机"。
