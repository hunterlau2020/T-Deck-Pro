## 1. 申请事由与触发问题（按 §11 修订程序）

本次修订旨在从制度层面纠偏“审查内卷与过度推演”，在坚守嵌入式安全底线（防变砖、防死锁、防泄密）的同时，降低追求完美倾向，恢复快速迭代能力。按 `docs/review_guide.md` §11 修订程序，指明五项触发问题与正反例：

### 触发问题 1：L1（设计）与 L2（实现）关注点混淆，伪代码被当作 C++ 源码做静态分析
- **现象**：审查者对设计稿中的流程示意伪代码，进行 C++ 内存布局、对象平凡可复制性（trivially copyable）、指针析构所有权的严格代码级审查。
- **反例**（OTA v5 Codex review）：Codex 指出设计稿中 `xQueueSend(ota_check_result_t{manifest})` 伪代码“若结构体含非平凡对象会发生字节拷贝导致悬空”，据此判定为 `B/2/静默 → P1` 并给出 C 阻断开工。
- **正例**：设计评审（L1）确认数据流向与业务语义正确即可。关于 `ota_check_result_t` 究竟使用定长 POD 还是分配堆指针移交所有权，属于实现期（L2）的常规编码决策，审查者应列为 `[Implementation Note]`，不阻断设计合入。

### 触发问题 2：“静默表”被滥用于纯文档评审，造成定级多跳级联膨胀
- **现象**：指引 §4.2 规定静默缺陷整体上移一级。审查者利用“设计稿天然没有串口日志输出”的特点，将文档中任何“未定义的边界情况”通过假设推演为静默致命缺陷（未定义 → 程序员未来写错 → 发生堆损坏 → 且表面无报错 → 查静默表升为 P1）。
- **反例**：文档未显式说明某个极端异常时序如何释放变量，审查者假定实现者必写出泄漏代码，且无日志报错，直接定级为 P1 并打 C。
- **正例**：静默表仅适用于运行态代码（CODE/HW）。文档（DOC）本身的表述缺失一律查有声表；除非方案在数学/逻辑上直接自相矛盾（如签名自指）或存在物理变砖隐患，否则假想性编码缺陷在设计阶段一律封顶 P3。

### 触发问题 3：缺乏复审增量范围锁定与轮次收敛上限（无休止开辟新战场）
- **现象**：作者根据上一轮评审意见修改了 A 问题，下一轮审查者却在未经修改的第 N 屏历史老段落中找出 B 问题；或者在修了 B 后又对 B 的修法衍生出 C 问题。轮次缺乏熔断机制。
- **反例**：OTA 设计 v4 集中于签名自指与 TWDT 喂狗，作者 v5 彻底修复后，审查者在第 5 轮回头挑出早先版本就存在的“Check 在飞离屏且用户再也不进该屏”的离屏排空问题，继续阻断。
- **正例**：复审轮严格锁定在“当前 diff 及其直接波及上下文 + 上轮缺陷闭合”。老段落非 P0 缺陷一律不得阻断当期合入，转入台账；设计评审拉扯达到 3 轮强制触发属主收敛裁决。

### 触发问题 4：审批三态缺乏弹性缓冲档，C 结论门槛过低
- **现象**：只要审查者列出一条 P2（甚至虚标的 P1），就只能在 A、B、C 中选择 C（部分接受）。而流程门禁 G-合入 规定 C 必须重新修复并重新走评审，导致微小意见立刻触发下一轮全量评审。
- **反例**：某文档仅有“格式编码未钉死”、“建议增加一段防护注释”等 P2/P3 意见，审查者因无合适中间档而直接打 C，逼迫作者重新发版。
- **正例**：增设 `A-（带跟踪项接受）`。对核心成立、仅存 P2/P3 的情况给出 A-，要求作者在代码编写时落实，免除重新发起设计评审的开销。

### 触发问题 5：多 AI Reviewer “军备竞赛”与一票否决
- **现象**：同时引入 4 个模型评审，模型为了体现严谨性竞相挖掘极其罕见的边界；只要有 1 个模型给出 C，作者就不得不全盘重来，4 票事实演变为“4 票中任意 1 票否决制”。
- **反例**：OTA v5 中 Claude 已经给出 `A 全量接受`，但 Codex 和 Grok 仍因细节给出 C，导致该设计无法开工。
- **正例**：建立“主审模型（Primary Reviewer）”负责制。其余模型作为旁审顾问，旁审的反例仅供主审与属主参考，不单独具备一票否决权。

#### 增补 1：[§1.1 适用范围裁剪] 补充设计评审（L1）边界定义
```markdown
### 1.1.1 L1 设计稿评审的边界与非目标（Out-of-Scope）

设计评审的目标是验证：系统架构可行性、协议与状态机完备性、硬件约束匹配度、威胁模型与回滚兜底策略。
为防止审查过度前置，特规定以下事项属于 **L1 阶段非审查目标**，严禁在设计阶段以此阻断：
1. **伪代码非生产代码**：设计稿中的伪代码仅用于表达业务语义与时序，严禁对其进行 C++ 语法、符号可见性、ABI、定长/变长内存布局的源码级静态分析。
2. **内存所有权与传参形式**：例如 FreeRTOS 队列使用定长 POD 值拷贝还是堆指针转移所有权、结构体是否 trivially copyable，明确属于 **L2（代码实现）** 阶段的决策。
3. **[Implementation Note]（实现期备忘）**：审查者发现的实现期潜在陷阱（如“队列传指针需防内存泄漏”、“任务创建失败需回滚标志”），统一归入结论中的《实现期备忘》章节。**此类提示严禁定级为 P0/P1/P2，严禁作为打 C 或阻断开工的理由**。
```

#### 增补 2：[§4.2 后果×可达性判定表] 补充定级防膨胀铁律
```markdown
### 4.2.1 定级防膨胀铁律（防静默表与假想推导滥用）

1. **静默表仅限运行态实体（CODE/HW）**：文档（DOC/SPEC）一律查有声表。文档没有显式报错日志是文档载体的客观属性，不得以此为由将规约未详述的问题按静默表上调一级。
2. **反假想级联推导（No Hypothetical Cascades）**：定级必须依据当前客观存在的证据，禁止以“如果开发者未来犯错可能会导致...”为前提进行灾难推导。凡需依赖“未来实现者写错”才成立的隐患，在设计阶段一律定为 P3（实现提示）。
3. **严格多前提折算（§0.7b）**：对于必须满足“特定极端时序 + 刚好未离开/重进页面 + 刚好队列满”等多重条件的缺陷，必须按最严苛前提折算为可达性 3（P3 或观察），严禁主观升格为 P1/P2。
```

#### 增补 3：[§2.3 代码审批三态] 升级为四态并限制 C 结论
```markdown
### 2.3 审批结论四态（升级 A- 档并收紧 C 门槛）

评审结论分为：**A 全量接受 / A- 带跟踪项接受 / B 退回重构 / C 阻断修改**：
- **A 全量接受**：设计/代码完全合规，无保留意见，直接合入/开工。
- **A- 带跟踪项接受（Approved with Notes）**：【新增】
  - **适用条件**：核心架构与主路径完全成立，无未解决的 P0/P1 缺陷；仅存在 P2 边缘场景或 P3/Nit 建议。
  - **允许动作**：**具备合入主线或开工资格，无需再发下一轮文档评审申请**。审查意见自动转为《实现期 Checklist》或登记 `issue_list.md`，在代码实现/真机回归时一并验证。
- **B 退回重构**：核心方向性错误、方案无法满足基本硬件/业务需求。
- **C 阻断修改**：
  - **严格准入门槛**：**只有存在当批引入且确凿可达的 P0/P1 致命缺陷（变砖、硬死锁、严重泄密），或严重破坏 §5 承重不变量时，方可给出 C 结论**。
  - **严禁滥用**：严禁仅因存在 P2/P3 问题、实现期备忘或理论推演意见而给出 C 结论。违者属主可直接推翻判定。
```

#### 增补 4：[§0. 评审原则] 增补审查增量锁定与轮次收敛
```markdown
4b. **增量审查范围锁定（Incremental Scope Locking）**：
    在复审轮（Round ≥ 2）中，审查范围严格锁定在：① 当期提交的 diff 区域；② 上轮被点名缺陷的修复有效性。
    **严禁在复审轮对前几轮未修改且未提出异议的历史既有段落发起新的非致命（非 P0）阻断性意见**。
    若审查者在复审时偶发获得新的非致命改进灵感，一律登记入台账作为后续优化，不得卡死当期合入。

11. **务实交付与边际收益递减（Pragmatic Engineering）**：
    本项目为嵌入式个人设备，真机实测是最可靠的试错手段。当纸面推演的边际成本超过真机验证成本时，应停止纸面辩论。
    **三轮收敛红线（Max-3-Rounds Rule）**：同一主题设计稿拉扯达到 3 轮时，强制触发属主收敛裁决。只要方案无物理变砖与泄密死穴，属主应裁定 A- 并批准进入代码编写与探针实测阶段。
```

## 6. 开发者自评（按 §7.1 强制项）

  1. **L1 非审查目标与 [Implementation Note] 的确立**：彻底切断审查者将伪代码当生产 C++ 代码严苛挑刺的机制，立即释放设计阶段的生产力。

  3. **静默表禁用规则**：从数学定级逻辑上遏制了将文档疏漏多跳推导为 P1 的漏洞。

- **最没把握的部分（强制列出 ≤3 处）**：
  1. **限制 C 结论门槛（仅限 P0/P1）是否会导致审查者强行将 P2 虚标为 P1**：
     - *防范机制*：在 §4.2 严格绑定判定表坐标复算，虚标 P1 若无明确的不可恢复/泄密证据，属主有权直接降级。

     - *防范机制*：若 diff 触及全局公用头文件，则受波及模块可审；纯局部文档或单屏私有逻辑，严格锁定 diff 区间。

     - *防范机制*：初期可由属主（用户）指定 Claude 或 Codex 为单期主审，其余模型输出作为附录参考。
