## 复核方法

两份提案诊断的是同一个真实现象（本轮独立验证，非采信申请书自述）：
读了 `docs/reviews/ota-update-design-review-result-e0ec3bb-codex.md` 与
`...-grok.md`（v5 轮实际结果），确认两份提案引用的"队列传 manifest
是否 POD/指针"（Codex P1）、"离屏排空点未写"（Grok P2）确有其事，且
Codex 把前者定级为 `B/2/静默 → P1`——**这正是两份提案共同拿来当"反例"
（不该挡开工）的那条发现**。这是本轮评审的关键测试用例：两份提案的
机制设计得对不对，就看它们套在这个真实案例上会不会算出"合理的结论"。

## 两份提案的共同诊断（成立）

- OTA v1-v5 前几轮挡住的都是真协议缺陷（框架提前自证、8s TWDT 误杀
  健康镜像、签名对象自指）——这几条无论按新旧规则都应该挡，两份提案
  都同意，也与本会话全程参与这五轮评审的实际记录一致。
- v5 起，签名自指等核心问题已闭合，但仍有 reviewer 用"队列谁 drain"
  "manifest 是否 POD"这类**实现期合同缺口**给 C、挡"开工"，导致每条
  这类发现的默认代价是"再开一版设计稿 × 四个模型全量复审"。这个代价
  与发现本身的严重度不成比例——两份提案对这一点的诊断都站得住。

## Grok 提案：机制评估（已落地，本轮验证为正确）

- **三类发现先分类**（§2.5.1）：协议/架构不可满足 → 挡 L1；**与仓库
  既有模块同构**的类型/调用/编码缺口 → 实现合同，不挡；完备性/文风 →
  不挡。**"与既有模块同构"这个限定词是整套机制里最重要的一句话**——
  它把"要不要挡"这个问题，从"reviewer 觉得严重不严重"的主观判断，
  换成了"这个决定在仓库里是否已经有一份已验证过的现成答案"这个可核实
  的事实问题。
- 用 Codex 那条 `B/2/静默 → P1` 的 manifest 所有权发现来验算这个机制：
  本项目对"worker `new` 结果、经队列交给 UI、UI `delete`"这个模式
  **已有明确、已定案、已真机验证的先例**——`docs/review_guide.md` §5.1
  异步 IPC 契约表第一行本来就写着这个模式，PenPal（`acc3893`）已经
  按这个模式跑通。所以"OTA 设计没有重申这个已有答案"确实符合
  §2.5.1"与既有模块同构"的判定，正确路由为 P2 实现合同，不必开 v6——
  Grok 的机制在这个真实案例上给出了合理结论。
- 明确不动 §4.2 的后果×可达性表、不动"P0/P1 不可作为已接受风险"、
  不动证据先行/证据>票数——只精确地在"设计稿该不该被实现细节挡住"这
  一个具体问题上开刀，不牵动整套定级体系。这种外科手术式的改法风险
  面小，容易独立复核，也是本轮建议采纳的主要理由。
- §2.5.4（落地文本合并进 §2.5.3 末段）"多方评审仅在首轮/疑似 P0-P1/
  属主点名时触发，收口轮默认一名 reviewer"——直接针对"四模型 × 每轮"
  的成本源头，且留了三个升级口子，不是无条件砍掉多模型复核。

## Claude 提案：机制评估（部分吸收，三项具体机制建议拒绝）

Claude 提案对问题的**诊断**（触发问题 1-5）基本准确，且额外指出了
Grok 提案没有单独点名的"多模型军备竞赛"现象（触发问题 5：4 个模型中
任意 1 个给 C 就等于一票否决）——这个观察本身是对的，本轮采纳。但
它提出的**三项具体机制**，逐一验算后都有问题，建议不采纳：

### 拒绝 1：静默表对 DOC 一律禁用（增补 2 第 1 条）

用同一条 Codex `B/2/静默 → P1` 的发现回测：如果按 Claude 提案"文档
一律查有声表"，这条发现会被强制按 `B/2/有声` 重算——**结果是 P2**
（对照 §4.2 有声表 B 行第 2 列）。也就是说，这条规则会把一个 Codex
正确识别、且这份仓库自己的历史（`= pp_state_t()` 压栈、memset
`std::string`）反复证明"文档阶段的沉默缺陷最终会变成真机堆损坏"的
真实静默类缺陷，**仅因为它出现在设计稿里**就机械降级，而不管它到底
静默不静默。这不是收紧口径，是关掉一个正确的判定通道，且这条规则会
对**任何**设计稿一视同仁地生效，不限于本轮想放过的那几类实现细节。
**已用一个来自本次真实评审记录的反例证伪，建议明确不采纳**——
`docs/review_guide.md` §4.2 增补段已经写了"DOC/SPEC 的表述缺口不得
因为文档本身没有运行日志而套用静默表"的反面（即维持原表，不新增
"DOC 一律有声"的机械规则），与本裁定一致。

### 拒绝 2：主审模型（Primary Reviewer）一票制（增补/触发问题 5）

回看这五轮 OTA 评审的实际记录：v3 轮的 8s TWDT 误杀是 **Grok** 先挖
出来的；v4 轮的签名自指是 **Codex** 先挖出来的；v4→v5 轮的取号副作用
是 **Grok** 先挖出来的；v5 轮的离屏排空缺口又是 **Grok**；manifest
所有权是 **Codex**。**没有任何一个模型垂直包揽了这五轮里的全部真实
发现**——如果本轮定了"主审"，其余模型降为"旁审仅供参考"，那么无论
指定谁做主审，历史上都存在至少一轮"真正的 P1 是被'旁审'挖出来的"
的反例。主审制会把"降低无效来回"的收益，换成"系统性漏掉某一类模型
擅长发现的问题"的风险，而这风险在本项目自己的历史里是可验证发生过
的，不是假设。**建议不采纳**；改用 Grok 提案的"多方触发条件"（首轮/
疑似 P0-P1/属主点名）来控制成本，既降低了无谓的复审轮数，又不固定
放弃某个模型的独立视角。

### 拒绝 3：三轮硬顶自动降级为 A-（增补 4 第 11 条后半）

这条是"轮次到 3 就强制属主裁 A-"，触发条件是**轮次计数**，不是**内容**
。Grok 提案的对应机制（§2.5.3）触发条件是"一轮复审没有协议/架构
P0/P1"，是**内容**触发。两者的差别在极端情况下很关键：如果真存在一个
需要 4、5 轮才能挖出来的深层协议缺陷（本次 OTA 签名自指恰好是在第 4
轮才被四方共同发现的），硬顶轮次数的规则会在第 3 轮就把设计强行推
出去开工，即便当时还有未闭合的真 P1；而 Grok 的内容触发不会有这个
问题——它只在"这一轮确实没找到协议缺陷"时才放行。**建议不采纳固定
轮次数触发**；如果确实需要一个兜底节流阀，更安全的形式是"轮次≥3 时
触发属主强制介入裁决"（裁决内容仍需检查是否有未闭合 P0/P1），而不是
"轮次≥3 自动给 A-"——但这属于锦上添花的补强，本轮不作为必须项，
现有 §2.5.3 的内容触发已经是合理、可工作的机制，不加这层也不算缺陷。

### 部分吸收：反假想级联推导

Claude 提案"禁止以'未来实现者可能写错'为前提做多跳灾难推演"这个
思路是对的方向，但**如果不加条件地整体采纳**，会与拒绝 1 犯同一种
错误——manifest 所有权那条发现，字面上也是"如果未来实现者选错了
POD/指针"的假设性推演，按无条件版本的这条规则也会被封顶到 P3。
`docs/review_guide.md` §2.5.1 现有文本已经吸收了这个思路的**正确
部分**："本款不允许以'未来实现者可能写错'为前提作多跳灾难推演；
**但若设计的缺失使任何实现都无法满足正文的安全或协议声明，仍按第
一行报告 P0/P1**"——用"是否存在任何可行的正确实现"这个可核实的
条件，取代了"是否需要假设未来会写错"这个不可核实的条件，同时避免
了把 manifest 那类真发现也一起封顶。这是本轮认为最好的处理方式，
已经在工作树的改动里。
