## 1. 触发问题

OTA 设计一日五版（v1→v5），每版 3–4 个模型整份 L1。前几轮挡住的是真 P1（框架提前自证、8s TWDT 误杀健康镜像、签名对象含 `sig`）。v5 架构已可开工后，仍有 reviewer 以「队列谁 drain」「manifest 是否 POD」等**实现合同缺口**拒绝 L1、给 C，倒逼 v6 × 多方。

同锚 `e0ec3bb` 已分裂：Claude **A + L1**，Codex **C**（甚至把未写对象布局升 P1），Grok **C**（离屏排空）。属主判断来回在放大，问是否过于追求完美。

根因在**现行指南的激励**，不在某一个模型「太较真」：

| 现行条款 | 实际效果 |
|---|---|
| §2.1 L1「所有伪代码/JSON 自洽」 | 未写 RTOS 布局 / 编码大小写 = 不给 L1 |
| §2.3 设计稿「用 L1–L4」、实践却套代码 A/B/C | 「A 不得挂必修项」→ 任何 P2 只能给 C → 新设计版 |
| §4.2「A 不得挂必修项」不分设计/代码 | 实现合同无法挂在设计 A 上绑 L2 |
| §7.2 对称三格①「全区间 diff」不区分设计复审 | 修一段 §2.1 仍整份当新架构重开 |
| 无轮次上限 / 无收口轮「一名 delta」 | 每条 P2 的默认成本 = 新版 × 四方 |

v1.2 没有「设计评审何时必须停」的收口规则。本申请补这一块。

**正例（修订后仍须挡 L1，给 C/B）**

- sha256 大小写 / 十进制无前导零未钉死。
- 因上述三项给 C、「不给 L1」、再开设计 v6。

## 3. 拟议规则（语义，供审对错）

1. **设计稿发现先分类再定级**
   - 协议/架构不可满足或按正文必错 → P0/P1，挡 L1，允许新设计版。
   - 实现合同缺口（与仓库既有模块同构的类型/调用/编码）→ P2 **应修@L2**，不挡 L1，**禁止**仅因此开设计 vN+1。
   - 完备性/文风/样本 → P3/Nit，不挡、不开新版。
2. **`NO_CONTRACT`（没写布局）不得直接升 P1。** 只有正文已经唯一可推断的写法不可满足，才是设计 P1。
3. **设计稿的 A ≠ 代码的 A。** 无协议/架构 P0/P1 时必须给 **L1+A**，可附实现合同清单绑 G-合入。因「还可以更完整」给 C = 违规。
4. **设计复审默认 delta**（本版 diff + 作者变化点）。扩面须声明「修复引入回归」或「新段与未改段矛盾」及段落。
5. **一轮无协议/架构 P0/P1 之后属主冻结设计**，下一对象是实现 commit。收口轮默认 **一名** reviewer 做 delta 闭合；多方仅：首轮 / 疑似 P0/P1 / 属主点名。
6. 新增门禁 **G-开工**（设计稿）：L1 + 无未闭合协议/架构 P0/P1。残留实现合同 P2 不挡开工。

**明确不改**：§4.2 后果×可达性表、P0/P1 不可风险接受（对**代码**与对**协议/架构类设计缺陷**仍成立）、证据先行、证据>票数、承重不变量清单、反例库。

### 4.7 在 §2.4 与 §3 之间新增 §2.5（本修订的承重段）

```markdown
### 2.5 设计稿收口（防把 L1 当成实现规格终稿）

设计评审的产出是 **G-开工**，不是一份可粘贴编译的固件规格。实现合同的门禁是
L2 / G-合入。规则不绑单一主题；OTA 设计 v1–v5 只作正反例来源。

#### 2.5.1 三类发现（设计稿专用，先分类再定级）

| 类 | 判定一句 | 挡 L1？ | 新开设计版？ |
|---|---|---|---|
| **协议/架构不可满足或按正文必错** | 最小修复必须改掉一段承重规范，否则合法输入全失败，或健康设备变砖/被系统性误回滚 | 是（P0/P1） | 是（C 或 B） |
| **实现合同缺口** | 最小修复是补一段与仓库既有模块同构的类型/调用/编码约定（队列谁 drain、结果指针 vs POD、hex 大小写、create 失败回滚计数） | 否（P2 应修@L2） | **否** |
| **完备性/文风/样本** | 校准矩阵格子、过时注释、用例按键路径与吞键矛盾 | 否（P3/Nit） | **否** |

**不得把 `NO_CONTRACT`（没写布局）直接升 P1。** 未写 = 实现选型，L2 二选一钉死。
只有「正文已经唯一可推断的写法不可满足」（如签名对象含 `sig` 自身）才是设计 P1。

正例（挡 L1）：签名对象把 `sig` 编进待签输入；自证窗口短于现有 `setup()` 阻塞。
反例（不挡 L1）：未写主循环排空结果队列；未写结果结构是 POD 还是指针移交；sha256 大小写未钉。

#### 2.5.2 设计稿的 A/B/C（与代码审批不同）

- **A + L1**：无协议/架构 P0/P1。允许附「实现合同」清单（P2/P3），绑实现 commit
  的 L2 / G-合入。那些项的门禁是代码合入，不是再改一版设计稿。
- **C**：仅当仍有未闭合的协议/架构 P0/P1，或承重方向仍错、必须改设计正文才能编码。
  C 的 required action 必须是「改哪一节规范」，不得是「请把实现细节再写完整」。
- **B**：推倒架构。

无协议/架构 P0/P1 时设计稿 **必须给 L1+A**（可附实现合同）。因「还可以更完整」
给 C = 违反 §0 原则 11。

代码评审维持原义：A 不得挂 P0/P1 必修；P2 应修进 `issue_list.md` 台账。

#### 2.5.3 复审范围 = delta（默认）

设计 vN 复审默认只核：`git diff <vN-1>..<vN>` 的规范性段落 + 作者列出的变化点。
未改章节当作已闭合，禁止当新架构重开。

扩面条件（须在结果头部声明段落）：① 修复引入回归（改措辞把已闭合声明改坏）；
② 新段与未改段直接矛盾。不得以「我还没核过那一节」扩面。

代码评审仍核全区间 diff（§7.2 对称三格 ①）。本款只约束设计稿。

#### 2.5.4 轮次与多方

- 同一设计主题：一轮无协议/架构 P0/P1 之后，**属主冻结设计**，下一评审对象是
  实现 commit。不得以残留实现合同缺口为由开 vN+1 再请多方。
- **收口轮**（作者声明无架构变更、只闭合上一轮 P2/P3）：默认 **一名** reviewer
  做 delta 闭合。其他模型意见是建议，不构成必须再开一版的票数（§0 原则 2）。
- 多方（≥2 模型）触发：首轮；本轮有疑似协议/架构 P0/P1；或属主点名。

#### 2.5.5 G-开工

见 §2.2 表。属主签字环节兜底（§0 原则 2）：模型给 C 但证据只支持实现合同缺口时，
属主可按 A 开工，并把该清单绑到实现申请。
```
