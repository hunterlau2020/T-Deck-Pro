## 1. Findings

### 1.1 真实 API Key 仍存在于源码、Git 历史和固件

- **严重性**：Critical
- **位置**：`examples/pda2/openai_api.h:62-67`
- **触发场景**：仓库、历史记录或固件被读取。
- **证据**：申请书明确继续遗留该项；NVS 无 Key 时仍使用源码默认凭据。
- **影响**：撤销当前 Key 只能阻止该 Key 继续调用，不能消除敏感信息泄露模式，也不能防止后续固件继续携带静态凭据。
- **最小修复**：默认 Key 改为空；清理 Git 历史并发布凭据轮换通告；启用 secret scanning。结果文档不得复制凭据正文。

### 1.2 Sleep 的等待发生在新屏加载前，触摸路径还会重入 LVGL

- **严重性**：High
- **位置**：
  - `examples/pda2/ui_deckpro.cpp:3894-3913`
  - `examples/pda2/ui_scr_mrg.c:62-70,180-219`
  - `examples/pda2/factory.ino:777-788`
- **触发场景**：从主菜单点击 Sleep。
- **证据**：
  - `scr_mgr_push()` 先调用目标页 `entry()`，之后才执行 `lv_scr_load()`。
  - 因此 `entry11()` 中的 `ui_disp_full_refr_sync()` 刷新并等待的是旧页面，不是 Sleep 提示页。
  - 点击路径本身处于 LVGL event callback 中；等待函数再次调用 `lv_task_handler()`，违反其“不得在 LVGL callback 中使用”的注释并形成重入。
- **影响**：主线程最多无响应五秒；Sleep 提示页真正加载后，倒计时仍可能立即开始而未等待该帧到达面板，原问题没有闭环。
- **最小修复**：不要在生命周期 `entry()` 中同步泵 LVGL。Sleep 页加载后，通过该页目标帧的 flush-complete 事件/序号异步启动三秒 timer；等待必须绑定本次 Sleep 帧，而不是全局布尔值。

### 1.3 扫描共享状态仍在临界区外读，竞态并未完全消除

- **严重性**：High
- **位置**：`examples/pda2/ui_deckpro.cpp:1884-1897,2312-2338`
- **触发场景**：WiFi event task 在 UI 等待 `SCAN_DONE` 时清除 `s_scan_release_pending`。
- **证据**：
  - 写入发生在 `s_scan_mux` 临界区内。
  - `wifi_cfg_scan_start()` 和 `wifi_cfg_scan_abort()` 的 `if`、`while` 及最终判断却直接在临界区外读取该非原子 `bool`。
  - 代码注释声明所有共享访问必须受临界区保护，但实现不符合该约束。
- **影响**：这是 C++ 数据竞争；UI 可能看不到回调清除结果，继续超时并显示 `Scan busy`，也无法用当前实现证明 `scanDelete()` 与迟到事件严格有序。
- **最小修复**：提供在临界区内读取 pending 的 helper，所有判断和轮询均通过该 helper；更适合使用 FreeRTOS event group/task notification 等待目标事件。

### 1.4 聊天日志原地整写且挂载失败自动格式化，断电或瞬时故障可清空历史

- **严重性**：High
- **位置**：`examples/pda2/ui_ai_chat.cpp:158-202`
- **触发场景**：保存 `/chat.log` 期间掉电、写满/短写，或 SPIFFS 瞬时挂载失败。
- **证据**：
  - 每次变更均以 `FILE_WRITE` 原地重写正式日志，没有临时文件、校验和或原子 rename。
  - `f.write()` 返回值完全未检查，失败仍表现为保存完成。
  - `SPIFFS.begin(true)` 会在挂载失败时格式化分区，与“不可用则 RAM-only”声明不一致。
- **影响**：一次消息发送、失败标记或清空操作都可能使已确认历史只剩有效前缀或全部丢失；瞬时文件系统问题可能被转化为永久数据删除。
- **最小修复**：禁止运行期自动格式化；写临时文件并检查每次写入、flush/close 后再原子 rename；记录版本、总长度和校验和，启动时只接受完整日志。

### 1.5 失败消息的 pending 状态和草稿未持久化，重启后会污染上下文

- **严重性**：Medium
- **位置**：`examples/pda2/ui_ai_chat.cpp:89-96,365-380,563-583`
- **触发场景**：请求失败后设备重启，再进入 AI Text 并继续对话。
- **证据**：
  - 日志只保存 `from_user + text`，不保存 pending/failed 状态。
  - `chat_pending_idx` 重启后恢复为 `-1`，textarea 草稿也未恢复。
  - 持久化正文已带 `(failed)`，加载后会被视为普通已发送 user 消息并进入后续 API context。
- **影响**：用户不能按申请书描述继续复用失败气泡；模型会把实际上未成功完成的消息及 UI 状态标记当成真实会话内容。
- **最小修复**：持久化消息状态和待重试草稿；构建 API context 时只选择 confirmed 消息，绝不发送 `(failed)` / `(truncated)` 等 UI 标记。

### 1.6 “整条轮次不拆”与实现不符，8KB 边界可能产生孤立 assistant 消息

- **严重性**：Medium
- **位置**：`examples/pda2/ui_ai_chat.cpp:272-299`
- **触发场景**：多轮历史接近 8KB，预算恰好落在一组 user/assistant 消息中间。
- **证据**：
  - 快照按单条消息从后向前选择，而不是按完整 user+assistant turn 分组。
  - 遇到第一条放不下的消息即 `break`，已经选择的下一条 assistant 仍会保留。
  - 串口所称 `context turns` 实际统计的是消息条数。
- **影响**：请求可形成以 assistant 开头、缺少对应 user 的上下文，模型记忆不稳定；验证日志也会误导定位。
- **最小修复**：显式构造完整轮次，仅成对加入预算；允许最后一个未获回复的 confirmed user，但不能保留孤立 assistant；日志区分 messages 和 turns。

### 1.7 Clear/New 是不可逆操作，却没有键盘路径和确认步骤

- **严重性**：Medium
- **位置**：`examples/pda2/ui_ai_chat.cpp:405-437,520-558`
- **触发场景**：以物理键盘操作 AI Text，或触摸误点 New。
- **证据**：
  - 键盘映射只有发送、滚动、删除和返回，没有 Clear/New。
  - New 点击后立即清空内存和持久化日志，没有确认或撤销。
  - 申请书称按钮为 Hist，最终代码和 UI 实际为 New，验收描述不一致。
- **影响**：无触摸/键盘优先流程无法开始新会话；触摸误操作会永久删除全部历史。
- **最小修复**：为 Clear/New 提供明确键盘焦点或快捷键；New 增加键盘可关闭的确认框，并同步申请书和真机回归步骤。

### 1.8 原子保存测试规格与实现矛盾，且仍未提供可执行失败注入证据

- **严重性**：Medium
- **位置**：`tests/test_nvs_atomic_save.md:20-38`、`examples/pda2/openai_api.cpp:26-94`
- **触发场景**：依据文档验证首次保存或空 Base。
- **证据**：
  - 实现中 active 缺失时按 slot 0 活动处理，因此首次保存写 slot 1；用例 2 却要求首次保存写 slot 0。
  - 用例 10允许保存空 Base，但 load 看到活动槽 Base 为空会回退旧平键/默认值，无法读回该次保存的完整三元组。
  - 文件本身明确只是“伪测试”，没有 mock、断言或实际执行结果。
- **影响**：申请书不能以“10 条失败注入用例”作为原子性已验证证据；后续执行者会按错误预期验收。
- **最小修复**：修正规格并落实可执行 Preferences mock 测试；至少覆盖首次迁移、各写入失败、提交失败、空值策略和重启读取。

### 1.9 用量统计是无同步的多键 read-modify-write，并发请求会丢计数

- **严重性**：Medium
- **位置**：`examples/pda2/openai_api.cpp:97-161`
- **触发场景**：离开 AI Config/AI Text 后旧请求仍在执行，同时从另一页面发起新请求，两项请求接近同时返回。
- **证据**：
  - 每个字段都以 `get + 本次值 + put` 独立更新，没有 mutex 或单写任务。
  - AI 请求允许跨页面继续运行，因此不满足单线程调用假设。
  - `begin()` 和八次 `put*()` 的结果均未检查，部分写入仍打印成功形态的 totals。
- **影响**：并发响应可互相覆盖增量，八个指标也可能来自不同批次；未来统计页展示的数据不可审计。
- **最小修复**：使用专用 mutex/统计任务串行累计；把全部指标作为一个带版本的 blob 一次提交，并检查持久化结果。

### 1.10 每次成功响应执行八次 NVS 提交，存在不必要的写放大

- **严重性**：Medium
- **位置**：`examples/pda2/openai_api.cpp:142-151`
- **触发场景**：持续进行 AI 对话或频繁执行 Config Test。
- **证据**：Preferences 的每次 `putULong64()` / `putDouble()` 都会提交 NVS；当前一次响应连续写八个键。
- **影响**：高频聊天会产生显著写放大、增加延迟并缩短 flash/NVS 可用寿命。
- **最小修复**：RAM 中累计后按时间/次数批量落盘，或一次写入完整统计 blob；Test 是否计入长期聊天统计也应在产品定义中明确。
