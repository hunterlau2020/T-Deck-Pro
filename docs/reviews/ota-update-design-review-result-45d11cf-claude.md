## Findings

### P2：`esp_task_wdt` 超时会真正复位，是 §5 全部回滚保证的唯一支点，但未被验证/未点名具体 sdkconfig 开关

- **位置**：`docs/ota-update-design.md` §5.2（"把 loopTask 显式订阅
  `esp_task_wdt`（8s 超时）...效果：自证前任何形态的死循环...8 秒内 WDT
  复位"）。
- **证据**：`esp_task_wdt_add()` 订阅任务后，超时的实际后果取决于
  `CONFIG_ESP_TASK_WDT_PANIC`（或等价配置）是否开启——若框架预编译
  sdkconfig 里这个宏是关闭的，TWDT 超时只打印一行警告继续跑，**不会
  触发任何复位**，那么 §5 整套"自证前挂死→WDT 复位→下次 boot 回滚"的
  保证就是空话，§8.1 a/b/c 三条回滚测试用例会在真机上直接失败。v3 对
  其余每一处硬事实都点了具体宏名/文件/行号（`CONFIG_BOOTLOADER_APP_
  ROLLBACK_ENABLE`、`CONFIG_MBEDTLS_ECDSA_C`、`CONFIG_MBEDTLS_ECP_DP_
  SECP256R1_ENABLED`），唯独这条全书**最关键**的机制性断言没有点名要
  查的具体开关，也没有标 `CLAIM_ONLY`——读起来像已核实的事实，其实是
  推理出的预期。
- **影响**：若假设为假 → 后果类 **A**（看门狗复位失效正是 §4.1 后果表
  自带的 A 类典型案例）、可达性 **1**（任何新固件的 setup() 意外挂死都
  会撞上，不需要特殊条件）、**静默**（不会有任何报错信号，直到你真的
  刷一个自毁固件并观察它到底有没有复位）——按静默表坐标 `A/1/静默 →
  P0`；但**验证状态为 UNKNOWN**（本环境无 `~/.platformio` 框架包，无法
  读 `sdkconfig` 确认该宏；也没有设备可实测），两轴不可互相推断
  （§4.3），所以不定成"已确认的 P0 缺陷"，而是**必须在 §8.1 a/b 两条
  回滚真测执行时第一时间验证的前提**——若真机测出"忙等 8s 后确实复位"，
  该前提即告 `VERIFIED`，本条自动降级为无需再跟踪；若测出"没复位"，
  按 A/1/静默 直接是 P0，且 §8.1 全部回滚用例的"预期结果"要重写。
- **两轴**：验证状态 `UNKNOWN`；契约符合性 `UNDECIDED`（决策项——不是
  设计逻辑错，是待验证前提）。
- **最小修复**：§7.3"受控基线"已经在收集 sdkconfig 里的其它宏，建议
  同批加一行：读框架 `sdkconfig` 确认 `CONFIG_ESP_TASK_WDT_PANIC=y`
  （或该核心版本等价的"超时即 panic/复位"配置项），把结果写进
  `docs/ota-baseline.md`；同时把 §5.2 的"效果：...8 秒内 WDT 复位"改成
  "预期效果（§8.1a 待验证）"这类措辞，避免推理被误读为已核实事实。

### P2：8 秒 WDT 窗口未与真机实测的"正常（无 bug）boot 到自证点"耗时做过比对

- **位置**：§5.2（"loopTask 订阅 esp_task_wdt（8s 超时）"）。
- **证据**：8 秒是一个看起来合理但未经标定的数字；`setup()` 里有多个
  外设初始化（EPD 选型、SD 卡、DRV2605、GPS/LoRa/4G 相关 GPIO 复位等），
  加上自证点还要等到 loop() 里第一次 `lv_timer_handler` 跑完——如果这条
  路径本身（一切正常、无 bug）在某些启动场景下（如某个可选外设探测
  超时更久）就逼近甚至超过 8 秒，会出现"固件本身没问题，却被自己的看门
  狗判定为挂死"的假阳性复位，反而制造一次不必要的回滚判定。这不是逻辑
  错误，是数值没有标定依据。
- **影响**：后果 **D**（边界正确性——超时阈值选择）、可达性 **3**
  （需要"某次启动恰好比平时慢"这种边界情况，不是每次都触发）、有声
  （复位本身会在串口留下痕迹）——`D/3/有声 → 观察`级，不阻断，但值得
  在验证计划里补一步。
- **最小修复**：§8 验证计划里加一条：真机测量"正常固件从 setup() 起点
  到自证点触发"的实际耗时（串口打时间戳），确认 8s 有 ≥2× 安全边际；
  若实测接近或超过 8s，上调超时值或拆分成"分阶段喂狗"（每个慢初始化
  步骤之间插 `esp_task_wdt_reset()`，这点 §5.2 本身已经要求，只是没有
  给出"验证过确实够用"的闭环）。

### P3：§8 验证计划缺一条 Codex P1-A（全局硬件锁）的直接并发复现用例

- **位置**：§8"验证计划"1-7 条；对照 §3.3"全局硬件锁与取消令牌"。
- **证据**：§3.3 的修复本身核对正确（`s_ota_hw_lock` 在 `Update.begin()`
  前 CAS 获取、跨页面/跨代次生效，直接解决了 Codex v2 轮 P1"gen 不能
  当写 flash 互斥锁"的原始复现路径——启动下载→离开 Settings 页→busy/gen
  已清→重进→尝试第二次 Update）。但 §8 的 1-7 条测试矩阵里没有一条明确
  写"离开 OTA 屏（下载进行中）→ 重新进入 → 尝试再次 Update → 确认被
  `s_ota_hw_lock` 拒绝，且原任务不受影响"——这是全书**唯一一条真正意义
  上的 P1**（Codex 定级）却没有专属回归用例，其它四条 P1/P1 级修复
  （TLS 隔离、签名、WDT 窗口、低电互斥）在 §8 都能对上明确的用例编号。
- **影响**：后果 **E**（验证计划完整性缺口，不是功能缺陷本身）、
  可达性 N/A——`E → 观察`，不阻断，纯粹是"补测试用例"级别的提醒。
- **最小修复**：§8 加一条第 8 项："下载中途离开 SCREEN2_2（Back）→
  重新进入 → 立即 Update → 确认第二次请求被拒绝（串口/UI 可见拒绝
  文案）且原下载不受影响、完成后状态正确"。
