## Findings

### P2：`s_ota_inflight` 递增时机与 PenPal 已确立的先例相反（实现合同，不挡 L1）

- **位置**：`docs/ota-update-design.md` §3.3（"`s_ota_inflight`
  （atomic，cap 1）在 `xTaskCreate` **成功后**递增"）。
- **证据**：v6 §3.3/§13 反复引用"PenPal `s_pp_inflight` 同款先例"作为
  这套单飞守卫设计正确性的依据。独立核对 PenPal 的**实际代码**
  （`ui_penpal.cpp:529-538`）：
  ```c
  /* count BEFORE create: the worker may finish on the other core before
   * xTaskCreate returns here (P2) */
  __atomic_add_fetch(&s_pp_inflight, 1, __ATOMIC_RELAXED);
  TaskHandle_t h = NULL;
  if (xTaskCreate(pp_task_func, "penpal", 1024 * 8, rq, 1, &h) != pdPASS) {
      __atomic_sub_fetch(&s_pp_inflight, 1, __ATOMIC_RELAXED);
      ...
  }
  ```
  PenPal 的实际顺序是**先递增、再 `xTaskCreate`，失败才回滚递减**，
  且代码注释明确写了原因："worker 可能在 `xTaskCreate` 返回给这边
  之前，就已经在另一个核上跑完"。v6 §3.3 把这个顺序**反过来**了
  （成功后才递增），恰好是 PenPal 那条注释专门警示要避免的写法——
  引用先例却写成了先例明确避免的反例。
- **本轮推演过程**（如实记录，含我中途推翻自己的判断）：先怀疑"递减
  在递增之前执行会让计数器永久卡死"——重新推演发现原子加减是可交换
  的，只要两次操作最终都会执行（v6 §3.3 本身也保证"递减在 worker 唯一
  出口"，不会被跳过），最终净值不会永久错误，我最初的"永久锁死"猜测
  不成立。真正的风险窗口是**瞬时**的：`xTaskCreate()` 返回成功到本核
  执行"递增"语句之间的几条指令间隙里，如果**另一个并发调用方**恰好在
  这个间隙读到"未递增"的旧值，会误判"未满员"而放行第二个 Check/Update
  ——这正是 PenPal 注释想避免的"cap 被瞬时突破"，不是我最初以为的
  "永久卡死"。但 OTA 的调用入口目前只有 UI 线程按键触发、单线程顺序
  执行（不像 PenPal 存在链式/多入口调用模式），我没能构造出一个具体
  的"第二调用方恰好在这几条指令间隙里发生"的可复现路径——按 §0.7b
  多前提折算，这条**可达性目前算不到确凿的档位**，倾向可达性档 3
  （需要与已知调用模式不符的并发触发条件）。
- **两轴**：`VERIFIED`（CODE：`ui_penpal.cpp:529-538` 原文核对无误，
  v6 正文原文核对无误，两者顺序确实相反）/ `VIOLATES`（v6 自称遵循的
  先例，实际未遵循——按 §2.5.1"与既有模块同构"的判据，这类问题的
  正确答案已经由 PenPal 决定，v6 没有理由另选一个）。
- **按 §2.5.1 定性**：这是**实现合同缺口**，不是协议/架构缺陷——语义
  已有可行实现（PenPal 那几行代码就是答案），修复零成本（交换两行
  顺序 + 把失败回滚也搬过来），不改变 OTA 的架构。**不挡 L1**，列入
  本结果的实现合同，绑定实现 commit 的 L2 / G-合入。
- **最小修复**：§3.3 改为"`xTaskCreate` **调用前**递增；失败立即回滚
  递减 + delete 快照 + 报错"，与 PenPal `ui_penpal.cpp:529-538` 逐行
  一致；顺带把这行改动的理由（"避免与已递增但尚未创建成功的窗口
  竞争"）搬进注释，供以后再有人对照。

## 已通过项（本轮独立复核，非转述 §13）

- **结果通道改指针传递**（Codex v5 P1 修复）：`xQueueOverwrite` 用于
  深度 1 队列、非阻塞发送，正确解决了 Grok v5 P2 指出的"worker 卡在
  满队列发送"问题；§3.1 自己承认"覆盖会丢一个未消费的结果结构"这个
  残余风险，并给出"每 tick 无条件排空"作为缓解——在当前单飞（cap 1）
  且入口单线程的前提下，这个残余窗口的可达性很低，作为设计阶段的
  已知边界记录是合适的处理方式，不必再加复杂度去彻底消除它。
- **自证语义修正**（Qwen v5 P2）——**本轮独立复核代码证据，结论成立**：
  - `factory.ino:229-241`：`display->firstPage(); do {...} while
    (display->nextPage());` 循环结束后，**无条件** `disp_flush_done_seq
    = disp_flush_req_seq`，不检查循环是否"正常"结束。
  - `lib/GxEPD2/src/GxEPD2_EPD.cpp:137-156`：`_waitWhileBusy` 用
    `micros() - start > _busy_timeout` 做**有界**超时；超时只
    `Serial.println("Busy Timeout!")` 后 `break`，不返回错误、不中止
    `nextPage()` 的其余流程。
  - 两处合起来确实证明了 v6 的结论：自证门控看到的 `done_seq` 更新，
    只代表"LVGL→EPD 软件序列走完了"，跟面板上是否真的显示出内容
    **没有必然联系**（BUSY 超时同样会让 `done_seq` 正常前进）。v5 把
    "屏坏会回滚"写进"已裁决事项"是过度声称，v6 用真实代码路径撤回
    这个声称、改为"会自证、不回滚（可接受，层 3 兜底）"，是本轮见到
    的最扎实的一次自我纠错——纠正了自己团队上一轮的一个错误论断，
    而不是等外部 reviewer 指出。
  - 顺带确认了一个 v6 没提但结果一致的细节：`_waitWhileBusy` 内部的
    `yield()`（:155，注释"avoid wdt"）喂的是 idle 任务的看门狗，不是
    v6 §5.2 新增的 loopTask 专属 `esp_task_wdt` 订阅——所以 v6 把这段
    库内等待归类为"不可喂 loopTask 的狗、只能靠 T 兜底"是准确的，
    不存在"其实库里已经喂了"的漏判。
- **TWDT add 失败守卫一致性**（Codex v5 P3）：伪代码改成"仅
  `e == ESP_OK` 才置位守卫"，与散文描述的失败处理一致，消除了 v5
  "失败却仍置位"的自相矛盾。
- **字节串编码钉死**（Grok v5 P3-1）：十进制无前导零、64 位小写 hex、
  UTF-8，并配了互测向量用例（§8.6/§8.5），把"两端各自合法实现却验签
  失败"这个此前只是提醒、没有钉死的风险关掉了。
