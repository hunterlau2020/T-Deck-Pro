## 复核方法

v4→v5 是"修复上一轮唯一 P1（签名自指）+ 收四方 P2/P3"的收尾轮。这类
收尾轮最容易在两个地方出问题：①声称修好的地方是不是真的自洽可执行
（不能只读 §0/§12 的处置摘要，必须逐字读被改的那段正文）；②之前几轮
"已确认无误、不必再查"的既有代码引用，这轮会不会因为用法变了而重新
出问题（例如 v4 曾经正确引用了 `ui_disp_full_refr_seq()`，但用法本身
在 v4 就已经错了，只是没人在 v4 那轮查到——这正是本轮 Grok 抓到的
P2-2，我自己在 v4 轮验证这两个函数"存在且被复用"时没有查到"调用方式
是否正确"这一层，是我上一轮的一个盲点，本轮据此加大了对"引用是否
真的存在"之外、"调用模式是否正确"这一层的复核力度）。

## 独立复核结果（逐条验证，不采信 §12 自报）

### 1. 签名对象自指（本轮唯一的历史 P1）——已正确修复

- **位置**：§2.1。
- **复核**：v5 把"签名对象"改回**显式六字段枚举**（version/url/size/
  sha256/seq/notes，逐字段加 `\n`），并新增一句"`sig` 不在签名对象
  内——它是对该六字段字节串的签名结果本身"，同时保留了 v4 两条真正
  的改进（JSON 值直接拼接、notes 禁换行）。逐字重读，确认不再有
  "sig 计入自己签名输入"的自指——这正是我上一轮（v4）指出的问题，
  修法与我上一轮建议的方向一致（恢复 v3 式枚举 + 保留 v4 两条澄清）。
- **验证闭环**：§8.6 新增"占位 sig + 六字段正确签名 → 通过"用例，
  把"sig 是否真的被排除在签名输入之外"这条规范性文字变成了一条可
  执行的测试断言，防止再退化成 v4 那种模糊表述。**已闭合。**

### 2. TWDT 句柄与喂狗守卫（Codex/Grok v4 轮 P2）——已正确修复，且独立验证了底层代码结构

- **位置**：§5.2。
- **复核**：`esp_task_wdt_add(NULL)`/`esp_task_wdt_delete(NULL)`（禁止
  把函数名 `loopTask` 当句柄传），与我自己 v4 轮的建议完全一致；新增
  `s_boot_wdt_subscribed` 守卫标志包住全部具名喂狗点，自证后关闭该
  标志——正好回应了我 v4 轮提出的"共享代码路径喂狗调用需要区分窗口
  期"的顾虑。
- **独立验证喂狗点的可行性**（本轮新做的工作，不是转述）：
  - 逐行重新推算 `A7682E_init()`（`factory.ino:501-540`）的失败路径
    耗时：`retry++ > retry_cnt` 是**后置自增比较**，需要 `retry` 从 0
    数到 6（第 7 次判断 `6>5` 才成立）→ `testAT(1000)` 实际执行 **7
    次**（7000ms）+ 断开重连分支 `delay(100)+delay(1000)`(1100ms) +
    前后 `delay(70+200)`ms = **8370ms ≈ 8.4s**——与 v5 §1 的修正值
    完全吻合（v3/v4 引用的"6.1s"确认偏低，v5 采用的"8.4s"是对的）。
  - 读了 `peri_gps.cpp:320-383` 的 `getAck()` 实现：外层是
    `while (millis()-startTime < 800) { while(SerialGPS.available()){...} }`
    ——**无 `delay()` 的紧凑自旋**，`GPS_Recovery()`（`:385-413`）就是
    连续调 4 次 `getAck()`，中间只有 `SerialGPS.write()`，没有额外
    `delay()`。这意味着"每轮插一次喂狗"在这两个函数里都是**天然可行**
    的——`testAT` 循环每轮 ≤1000ms 一次喂狗、`getAck` 自旋循环里插一次
    几乎是零成本的高频喂狗——喂狗后**真正的最大间隔**是约 1-1.1 秒级
    （testAT 单次超时 / 断开重连分支的 1100ms），远小于 T 的 30s 下限。
    v5"T 约束的是喂狗间隔而非总时长"这个重新定义站得住，不是文字游戏。
- **已闭合**；无新增疑点。

### 3. `ui_disp_full_refr_seq()` 取号副作用（Grok v4 轮 P2-2）——已正确修复

- **位置**：§5.2 伪代码、§1 现状盘点。
- **复核**：v5 明确要求"只调用一次存变量；轮询只读 `ui_disp_flush_
  done_seq()`"，并把该函数的副作用（"触发整刷 + `disp_flush_req_seq
  ++`"）写进了 §1 的事实盘点里，不再是一个容易被忽略的隐藏细节。
  这一条是 v4 遗留的一个真实、容易踩的坑（若在轮询表达式里重复调用
  取号函数，每次轮询都会重新发起整刷并把目标序号往后推，判定条件
  永远追不上——首帧完成永远"未达标"，自证永远不会发生，等效于每次
  OTA 之后都被 T 秒 WDT 复位再回滚）——**这不是我自己发现的**（我在
  v4 轮验证过这两个函数"存在、且已被 WiFi 扫描覆盖层/Sleep 正确复用"，
  但没有去检查 v5 之前那版设计文字里的调用**表达式**是不是复制了
  正确用法——这是我上一轮的一个盲点，记在这里以便后续不再重复），
  是 Grok 本轮抓到的；本轮我做的是独立重读 `ui_deckpro_port.cpp:33-50`
  确认"取号"和"查询"确实是两个不同函数、且现有两处消费者
  （`ui_deckpro.cpp:2808/2830`、`:4518/4494`）确实是"取号存变量→之后
  只读查询函数比较"的模式，v5 的伪代码写法与这个已验证模式完全一致。
  **已闭合。**

### 4. 单飞守卫 `s_ota_inflight`（Qwen v4 轮 P2-1）——设计自洽

- **位置**：§3.1、§6、§8.4。
- **复核**：与 `s_ota_hw_lock`（专管实际写 flash 互斥）职责不重叠——
  `s_ota_inflight` 是更宽的"是否有任何 OTA 网络/worker 操作在飞"闸门，
  覆盖 Check 阶段（`s_ota_hw_lock` 这时还没取，因为还没到
  `Update.begin()`），且不受页面 `busy`/`gen` 复位影响，直接解决了
  "Check 在飞时离页重进又发起一次 Check"这个 `s_ota_hw_lock` 管不到
  的空当。与已验证过的 PenPal `s_pp_inflight`（`acc3893`，已真机验证）
  是同一模式的复用，不是新发明的机制，风险低。**通过。**

### 5. 快照所有权链（Qwen v4 轮 P2-2）——设计自洽，TOCTOU 关闭方式正确

- **位置**：§3.2、§8.5。
- **复核**：manifest 的生命周期——worker 验签后随结果队列**移交** UI
  →UI 在 CONFIRM_WAIT 期**独占持有**（用于展示的就是这份，不再重新
  读取任何共享/静态变量）→ 用户确认时做 **launch-time copy** 进
  Update 任务自己的结构。全程没有一个"多个阶段共享同一个可写缓冲"的
  时间窗，`s_ota_manifest` 这类静态共享变量被显式排除——"用户确认看到
  的包 = 最终刷入的包"这条不变量在结构上成立，不依赖运气。**通过。**

## 两处自评请求裁定，本轮给出明确答复

- **EPD 首帧完成作为自证门控，会把"系统健康但屏幕坏了"的固件也判定
  为失败并回滚，是否接受**：**接受**。这台设备的交互完全依赖 E-Paper
  （无其它显示通道，键盘/触摸脱离视觉反馈本身就不可用），"能启动但
  看不见任何东西"从用户角度等价于砖——与其让用户拿到一台"系统健康但
  黑屏"的设备去走 USB 恢复流程，不如让它在下次开机时自动回滚回能看见
  东西的旧版本。"自证语义 = 用户可见可用"这个定义对这台设备是正确的
  产品判断，不是过度保守。
- **喂狗点覆盖完备性依赖实现期审计，设计本身无法穷尽未来新增的长阻塞
  段**：这是诚实的、合理的残余风险披露，不要求本轮补齐（本来就补不
  齐——设计稿不可能预知未来谁会往 `setup()` 里加什么）。建议审计时
  特别注意区分两类阻塞：**有天然重试/自旋循环边界**的（如
  `A7682E_init`/`getAck`，可以照抄"每轮插一次"）和**单次不可拆分的
  长 `delay()`/无进度回调的阻塞库调用**（无法用"每轮插一次"的方式
  处理，需要整体挪到窗口外或缩短本身）——§10 的实现合同目前写的是
  "任何 >T/4 的新增阻塞段需要同步插喂狗点"，建议补一句区分这两类，
  否则遇到第二类时"插喂狗点"这个指导本身就不可执行。

## 对称三格

1. **是否核了全区间 diff**：是，另外主动重新推算了 §1 引用的
   `A7682E_init`/`GPS_Recovery` 具体耗时（不满足于"数字与上一轮一致
   就不用查"），确认 v5 的"8.4s"修正值本身也是对的，不是抄错了另一
   个同样错的数字。
2. **快照是否独立复跑**：仓库内可读代码（EPD 序列号函数、A7682E/GPS
   阻塞路径）全部独立 `Read`/逐行推算复核；框架 TWDT API 行为无环境
   验证，如实标 `UNKNOWN`。
3. **对"最没把握"处构造反例**：对自评①（喂狗完备性）尝试构造"存在
   不可拆分长 delay 的反例"，确认当前**已知**的四类阻塞（A7682E/GPS/
   EPD/PCM）都有天然的循环边界可插喂狗点，反例未在**已识别**范围内
   成立；对自评③（EPD 门控的产品取舍）未构造出反例——认为该决策
   对本设备是对的，直接采纳作为已裁决事项更合适，而不是继续悬置。
