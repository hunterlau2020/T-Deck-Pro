## 1. Findings

### 1.1 进入 AI 对话屏后看不到当前生效的端点、模型与 Key 摘要

- **严重性**：High
- **位置**：`docs/allinone-design.md:160-163`、`docs/allinone-design.md:167`
- **触发场景**：用户配好 AI 后进入对话屏发问；或多人共用设备，下一用户不知道上一用户配的是什么；或调试"为什么回答风格变了"时无法在屏上对照。
- **证据**：
  - §4 AI 对话屏交互仅描述输入态与发送行为，没有定义"状态条 / 标题区"显示当前 `endpoint` / `model` / `key 摘要`。
  - §4 AI 配置屏的 Key 标签固定为 `sk-or-v1-***`，且仅在配置页可见。
  - §9 风险 10 写明 Key 以明文存 NVS 但承诺"不打印到日志"——意味着对话屏也不能从日志读出。
- **影响**：
  - 用户不知道自己正用 OpenRouter 还是某个国内自建端点，回答风格/合规差异无法关联到配置。
  - 多人共用设备时不知道"这是为我配的还是上一位用户配的"，误发问题到别人账号。
  - 调试"为什么回答不对"时被迫来回切到 AI Cfg 屏比对，效率低。
- **最小修复**：
  1. AI 对话屏标题区常显一行状态条：`M: deepseek-chat · https://.../v1 · Key: ****a1b2`，超宽时省略中间段、保留末尾 4 位。
  2. Key 摘要采用通用末尾 4 位形式（不在屏上显示 OpenRouter 专属前缀），与配置页统一。
  3. 至少在输入态空框时显示该摘要，避免占用输入区；发送态、回答浏览态可继续显示。

### 1.2 AI 对话页"无草稿恢复锚点"，任何导航中断都会丢失问题

- **严重性**：High
- **位置**：`docs/allinone-design.md:160-163`、`docs/allinone-design.md:165-166`
- **触发场景**：用户输入完整问题后按 Enter，因 WiFi/Key/超时失败想改配置或重试；或回答滚动浏览时想微调首句以追问。
- **证据**：
  - §4 AI 对话屏交互未定义"输入草稿"的持久化位置、保留时机与失效时机。
  - §4 AI 配置屏交互只说"末字段 Enter 存 NVS 并退出回 AI 对话屏"——没说退出时是否带原对话草稿。
  - §9 风险 10 接受同步阻塞 15-30s，意味着发送期间用户最可能想"先去改一下 Key"——按 Backspace 退菜单、进 "8 AI Cfg"、改完再回对话屏，原问题是否还在，没有任何承诺。
  - 同日技术评审 `allinone-ai-interaction-review-result.md:160-163` §1.1 提到保留对话草稿，但未定义其在多次进出 / 多次失败 / 切屏竞态下的具体存活边界。
- **影响**：
  - 首次使用的"失败 → 改配置 → 重试"闭环依赖整段问题必须重打。
  - 回答翻页浏览时想微调首句以追问，必须先完整退到输入态、记下要改的字段、再翻页对照——严重打击追问意愿。
- **最小修复**：
  1. AI 对话屏维护独立 `chat_draft` 缓存：进入屏时按 Enter 发送则清空；任何失败 / 退屏 / 进 AI Cfg 不清空；下次进入屏时若缓存非空且输入框为空，自动恢复。
  2. 浏览回答时按 Backspace 回输入态不丢草稿；按 Backspace 退菜单则草稿保留至下次进入。
  3. AI Cfg 入口跳转需"对话页 → 配置页 → 返回对话页"全程带草稿；在配置页底部加 `Back to Chat` 提示（即便无触摸，至少在屏上文字明示）。
  4. 草稿超长（如 200 字问题）也要保留，不要因缓冲区限制静默截断。

### 1.3 AI 配置屏"无取消语义"，修改中途放弃只能反向 Backspace 一路退出

- **严重性**：High
- **位置**：`docs/allinone-design.md:165-166`
- **触发场景**：用户进入端点字段想修改 Key 字段时发现上一字段其实是对的；或尝试了几个字符后觉得不需要改；或中途发现 Key 拼错但又想保留旧可用 Key。
- **证据**：
  - §4 AI 配置屏交互只定义 Enter 跳下一字段 + 末字段保存退出 + Backspace 退格 / 回上一字段。
  - 没有"取消本次编辑""恢复到进入时快照""放弃本次改动"动作。
  - §9 风险 10 写明 NVS 写入与读取，但没有撤销机制。
  - 同日技术评审 `allinone-ai-interaction-review-result.md:165-166` §1.2 提到"采用与 WiFi 配置相同的显式状态设计"但未具体落到取消语义。
- **影响**：
  - 想回到上一字段，必须先把当前字段全部删空；想放弃本次所有修改，必须一路 Backspace 退到首字段再退屏，期间每一字段的中间状态是否被回写 NVS 还是仅在退出时一次提交？设计未定义。
  - 与 WiFi 配置屏（§4 L141-149 的双模式状态机）相比，AI 配置的"离开"语义严重缺失：WiFi 配置有"扫描前 vs 扫描后""编辑 vs 选择"明确区分，AI 配置只有"线性 3 字段"。
  - 在墨水屏上，用户对"现在存没存"没有强反馈——误退等于误保存。
- **最小修复**：
  1. 显式状态机 `ai_cfg_state { EDITING, CONFIRM_SAVE, CONFIRM_DISCARD, TESTING, SAVING, SAVED }`。
  2. 进入屏时拍快照；编辑不写 NVS；末字段 Enter 进入 `CONFIRM_SAVE` 二次确认。
  3. 任意位置 Backspace 退屏触发 `CONFIRM_DISCARD`：`Discard changes? Y=Enter / N=any key`，确认后恢复快照并退出。
  4. 与 WiFi 配置屏（§4 L141-149、§5.3 L218 `ui_wifi_config.cpp` 行）保持同一交互范式，便于用户复用肌肉记忆。

### 1.4 错误提示信息不带可执行动作入口，用户看到失败后只能盲走

- **严重性**：High
- **位置**：`docs/allinone-design.md:162-163`
- **触发场景**：用户首次发问时缺 WiFi 或 Key；或 Key 错误返回 401；或模型名拼错返回 404；或 TLS 时间未同步返回证书错误。
- **证据**：
  - §4 AI 对话屏交互只定义 `Set WiFi / Set AI Key` 静态文字提示，没有键盘可达的对应动作。
  - §4 AI 配置屏交互对 401/403/404/超时/TLS 等具体错误完全没有 UI 路径。
  - §9 风险 10 同步阻塞最多 30s 后失败，失败信息如何分门别类到达用户，设计空白。
  - 同日技术评审 `allinone-ai-interaction-review-result.md:162-163` §1.6 给出错误分类表，但缺少"每类带哪些键盘入口"的落地。
- **影响**：
  - 用户看到 "AI error - check cfg" 或 "Set WiFi" 后只能按记忆操作，去配置页看看、再回来重试，反复来回。
  - 401 与 404 文案相同时，会被引导去改 Key（错）或改模型（错），完全靠试错。
  - 30 秒同步阻塞后用户已被失败震住，再做"先退出再看配置"这种反直觉操作体验尤其差。
- **最小修复**：
  1. 失败提示采用结构化两行：上行为错误类别（`401 Auth` / `404 Model` / `Timeout` / `No WiFi` / `No Key` / `TLS time`），下行为可执行动作（`Enter=Open Cfg / Sym-1=Retry / Back=Cancel`）。
  2. 区分"修 WiFi"与"修 AI Cfg"——前者跳 `SCREEN_WIFI_CFG_ID`（菜单 "6"），后者跳 `SCREEN_AI_CFG_ID`（菜单 "8"）。
  3. 错误信息保留原问题草稿（与 §1.2 联动），配置返回后可直接 Retry 而不必重打。
  4. 进入配置页修改后再回对话页，错误类别横幅重新显示直到下一次发送成功，避免"修了但不知道修了什么"。

### 1.5 末字段 Enter "隐式保存"缺少前置确认，错误配置直接覆盖可用配置

- **严重性**：Medium
- **位置**：`docs/allinone-design.md:165-166`、`docs/allinone-design.md:220`
- **触发场景**：用户第一次配置 AI，Key 末尾多打或漏一个字符、模型名拼错、端点漏 `/chat/completions`，按 Enter 直接退出。
- **证据**：
  - §4 AI 配置屏交互明文："末字段 `\n` 存 NVS 并退出回 AI 对话屏"。
  - §5.3 L220 `ui_ai_cfg.cpp` 行描述同。
  - §4 L168 字段允许字符表"小写 + `0-9 . : / - _`"，且"OpenRouter Key `sk-or-v1-...` 可直接输入"——`sk-or-v1-` 含连字符外的字母，键盘层可达，但字符约束未覆盖大写（Key 中常见）与 `+`（Key 中罕见但部分厂商含）等真实 Key 字符。
  - 没有"先 Test 再 Save"的两步式、没有格式校验、没有"覆盖前展示旧值"对比。
- **影响**：
  - 用户在墨水屏上看不见自己输入的字符与已存字符差异，一次 Enter 就把可用配置覆盖成无效配置。
  - 后续在 AI 对话屏看到 401/404 时，已无法想起刚才覆盖前的可用 Key 是什么。
  - 多人共用设备时尤其严重：A 覆盖 B 的可用 Key 后，B 只能联系 A 才知道之前的 Key 是什么。
- **最小修复**：
  1. 末字段 Enter 不立即写入 NVS，先进入 `CONFIRM_SAVE` 状态展示草稿与旧值的对比（或至少展示草稿摘要），按 Enter 二次确认才写入。
  2. 校验 URL 必须 `https://` 开头且路径非空；模型名非空；Key 长度 ≥ 16 字符。校验失败在屏内明示，不要直接退出。
  3. 提供 `Test` 入口（见 §1.10），测试成功后允许 Save；失败不写 NVS。
  4. 提供 `Reset to defaults`（恢复 OpenRouter 端点 + 清空模型 / Key），键盘可达键位（如 Sym-0 或 Alt+R）。

### 1.6 发送态与浏览态切换语义模糊，发送期间按键 FIFO 集中释出会破坏后续输入

- **严重性**：Medium
- **位置**：`docs/allinone-design.md:160-163`、`docs/allinone-design.md:219`
- **触发场景**：用户按 Enter 发送后立即补打几个字符，或发送成功后浏览回答时按 Backspace 又按 Enter。
- **证据**：
  - §4 AI 对话屏交互只说"`\b` 返回菜单"，但发送中、浏览中、错误态的 Backspace 语义未区分。
  - §5.3 L219 `ui_ai_chat.cpp` 描述"发送成功后清空输入框（浏览态 `\b` 语义无歧义）"与"浏览回答时按任意可见字符自动回输入模式并追加该字符"——但发送中、发送失败、等待重试时的输入缓冲策略未定义。
  - §2.2 字符 FIFO 16 深 + `keypad_clear_chars()` 在切屏时清空——意味着发送期间按键进入 FIFO 但未被消费；完成时这些按键集中释出，可能触发意外动作（甚至可能在用户以为"已取消"时进入输入态后批量注入）。
- **影响**：
  - 发送时手快按 Enter 不会发第二次（好），但期间按其他字符会在完成后批量进入输入态，无声改变用户意图。
  - Backspace 在浏览态与输入态含义不同（前者翻页 / 退出，后者删字），用户跨态切换时易误删刚输入的字。
- **最小修复**：
  1. 发送中屏蔽所有非 Cancel 类输入；完成后**丢弃**发送期间累积的 FIFO 字符（不要批量注入输入框），与 `keypad_clear_chars()` 的"切屏清残留"语义对齐。
  2. 浏览态顶部小字提示 `Back: page up / Enter: next / Char: edit`，明确 Backspace 双语义。
  3. 失败态进入后输入框保持上次草稿但禁用可见字符追加（避免错误信息闪烁时误打），待用户明确按 Enter 才回到输入态。
  4. 双击 Enter 防抖：发送态判定 Enter 后置 `chat_send_lock=true` 直到收到响应或失败，重复 Enter 直接忽略。

### 1.7 模型与端点"自由输入"未提供任何预设、历史或纠错辅助

- **严重性**：Medium
- **位置**：`docs/allinone-design.md:30-31`、`docs/allinone-design.md:165-168`
- **触发场景**：用户首次配 AI，不知道该用什么模型名；或资深用户在 OpenRouter 与自建端点之间切换，记不住命名空间规则；或拼错模型名（如 `deepseek-chat` 缺 `deepseek/` 前缀）后看到 404。
- **证据**：
  - §1 L30 已确认决策"模型手动输入，**不做厂商预置快捷项**"。
  - §4 AI 配置屏交互："模型手动输入（如 `deepseek/deepseek-chat`...）"——纯文本提示，没有可选项。
  - §4 L168 字符约束"小写 + `0-9 . : / - _`"，但不约束格式（OpenRouter 用 `provider/model` 形式，OpenAI 仅用 `model` 形式），用户在两种服务间切换容易混淆。
- **影响**：
  - 首次使用者面对空文本框需要查文档，键入"随便试试"必然 404。
  - 资深用户在 OpenRouter 与自建端点切换时记不住模型命名空间规则，反复 404。
  - 配置好模型后无法在屏上快速浏览"我之前用的那几套模型"，复用门槛高。
- **最小修复**：
  1. AI 配置屏模型字段下挂一个"最近 3 次成功用过的模型"短列表（本地缓存 `ai_model_history`，仅记录响应 2xx 的模型名），用 Sym 层 `+/-` 循环选择填空。
  2. 端点字段保存"最近 3 次端点"短列表，同样可循环复用。
  3. 配置页底部署名与端点的格式提示，例如端点字段下小字"`https://host[:port]/v1`"，模型字段下小字"`provider/model` for OpenRouter"——不破坏"不做厂商预置快捷项"决策，仅作为格式提示与用户自己的历史值快捷方式。

### 1.8 API Key 在编辑态明文 + 墨水屏残影 = 旁观可见

- **严重性**：Medium
- **位置**：`docs/allinone-design.md:165-168`、`docs/allinone-design.md:267-280`
- **触发场景**：用户在公共场合（会议室、咖啡馆、共享工作空间）配 Key，旁边有人瞥屏。
- **证据**：
  - §4 AI 配置屏交互：编辑时"文本框显示明文"。
  - §9 风险 3（L267-280）详细讨论 EPD 局部刷新残影与周期性全刷策略——意味着输入框每输入一个字符都触发局部刷新，墨水屏在连续输入后会留下字符叠加残影。
  - §5.3 L220 `ui_ai_cfg.cpp` 行描述未定义"输入完成离开字段时是否强制全刷"。
- **影响**：
  - 即便配置页做了密码模式显示，编辑态切换到明文的瞬间旁人可见 + 残影放大可见。
  - 残影在多次局刷后可能保留数秒到数十秒（评审 §9.3 详细讨论），旁人侧视可读。
- **最小修复**：
  1. 默认密码模式显示（`•`），仅在用户主动按指定组合键（如 Alt+R for Reveal）后才显示明文；5 秒自动恢复掩码。
  2. 离开 Key 字段时强制一次 `setFullWindow()` 全刷（虽然慢 1-2s，但 Key 是低频操作，可接受），配合 §9 风险 3 方案 A 计数器。
  3. 全屏右下角小字提示 `Key in edit. Move away to mask.`，与 §1.3 状态机联动。
  4. 与 §1.5 末字段二次确认机制结合：确认保存后再做一次全刷。

### 1.9 AI 对话屏回答浏览无页码 / 进度指示，长文翻页体验差

- **严重性**：Low
- **位置**：`docs/allinone-design.md:160-163`、`docs/allinone-design.md:219`
- **触发场景**：模型返回 800 字以上的回答，分多页；用户想跳到末页或返回第一页。
- **证据**：
  - §4 AI 对话屏交互："`\b` 返回菜单"——只说返回没说分页规则。
  - §5.3 L219 `ui_ai_chat.cpp` 行"分页显示回答"未定义总页数与跳转。
  - §9 风险 10 接受 30s 超时，意味着回答可能确实很长。
- **影响**：
  - 用户不知道自己在第几页、还有多少页，需要逐页试。
  - 只能 `Enter 下一页` / `Backspace 上一页`，无跳转。
  - 配合 §9.3 EPD 全刷昂贵，每翻一页若触发全屏渲染，操作不流畅。
- **最小修复**：
  1. 标题区加 `Page 2/5` 进度指示（与 §1.1 状态条共用同一行）。
  2. 提供首末页跳转键（建议 Sym-0 到首、Sym-9 到末）。
  3. 翻页只做局部刷新（不触发 §9.3 全刷计数器），仅在进入屏和退出屏时各做一次全刷。

### 1.10 AI 配置后没有"测试连接"动作可用

- **严重性**：Low
- **位置**：`docs/allinone-design.md:165-168`、`docs/allinone-design.md:54-81`
- **触发场景**：用户配完端点 + 模型 + Key，希望在离开配置页前确认能通。
- **证据**：
  - §4 AI 配置屏交互三个动作：Enter 跳字段、Backspace 回退、末字段 Enter 存盘。
  - §4 L168 没有 Test 入口；§2.3 L81 提到 AI Cfg 屏勾选 Trust self-signed——有开关建议但没有测试按钮建议。
  - §9 风险 10 接受同步阻塞 15-30s，意味着用户实际在配置后必然要回到对话屏发一次试错才能验证。
- **影响**：
  - 首次配置无法验证连通性，只能发问后等 15-30s 失败再回来排查。
  - 与 WiFi 配置屏"连接成功才存 NVS"的成功即保存策略相比，AI 配置没有同等"成功即放行"的反馈。
- **最小修复**：
  1. 配置页加 `Test` 入口（Sym-T 或 Alt+T 译 `'\x14'`），发一个最小请求（如 `GET /models` 列表），根据 HTTP 状态分类显示。
  2. Test 通过才允许 Save（与 §1.5 二次确认联动），失败提示具体错误类别（与 §1.4 错误分类表统一）。
  3. Test 期间屏蔽其他字段编辑，避免半配置状态被保存。
  4. Test 结果保留至下一次 Test 或下一次编辑，覆盖前明示。

## 3. 建议的产品状态机（流程层补充）

### 3.1 AI 配置页（流程层）

| 状态 | 进入条件 | 用户可见文案 | 允许动作 | 离开动作 |
|---|---|---|---|---|
| EDITING | 首次进入或字段切换 | 字段标签 + 当前值（Key 掩码） + 格式提示 | 字符追加、Backspace 退格、Alt+方向键切字段、Alt+T Test | 末字段 Enter → CONFIRM_SAVE |
| CONFIRM_SAVE | 末字段 Enter | `Save? <草稿> replaces <旧值>` | Enter 二次确认 → SAVING；Esc/任意字符 → 回 EDITING | Save → SAVING；Cancel → EDITING |
| TESTING | EDITING 中按 Alt+T | `Testing...` + 倒计时 | Backspace 取消 → EDITING | 完成 → TEST_RESULT |
| TEST_RESULT | TESTING 完成 | `OK: <status>` 或 `<error class> <fix>` | Enter → CONFIRM_SAVE；Backspace → EDITING | — |
| SAVING | CONFIRM_SAVE 后 | `Saving...` | 无 | 成功 → SAVED；失败 → EDITING + 错误 |
| SAVED | 写入成功 | `Saved.` 短暂全刷 | Enter → 返回对话屏 | 返回对话屏带草稿 |
| CONFIRM_DISCARD | 任何位置 Backspace 退屏 | `Discard changes?` | Enter 确认；任意字符取消 | 确认 → 返回并丢弃；取消 → EDITING |

### 3.2 AI 对话页（流程层）

| 状态 | 进入条件 | 用户可见 | 草稿 | 允许动作 | 离开 |
|---|---|---|---|---|---|
| INPUT | 进入屏 / 失败恢复 / 字符回输入 | 输入框 + 端点模型摘要 + 错误行 | 保留 | 字符输入、Backspace 退格、空框 Backspace 退菜单 | Enter 发送 → SENDING |
| SENDING | 提交请求 | `Thinking...` + Cancel 提示 | 保留 | Backspace 取消 → INPUT/FAILED；其他屏蔽；完成后清 FIFO | 完成 → ANSWER / EMPTY；失败 → FAILED |
| ANSWER | 收到响应 | 分页回答 + `Page X/Y` | 清空（已发送） | Enter 下一页、Backspace 上一页 / 回 INPUT、字符回 INPUT 追加 | 翻页 → ANSWER；首页 Backspace → INPUT |
| FAILED | 收到错误 | 错误类别 + 可执行动作 | 保留 | Enter 跳配置页；Sym-1 重试；Backspace 退菜单 | 配置/重试/退 |
| NO_CONFIG | 启动时检查 WiFi/Key 缺失 | 静态提示 + 入口 | 保留 | Enter 跳对应配置；Backspace 退菜单 | 同上 |

## 4. 用户旅程：首次使用闭环（评审视角）

评审把"用户首次开机 → 用上 AI"作为关键流程反推，发现以下断点：

1. **首次进入对话屏**：键入问题 → Enter → 看到 `Set WiFi / Set AI Key` 静态文字（§1.4 痛点）→ 退菜单 → 选 "6 WiFi Cfg" → 配好 WiFi → 返回菜单 → 选 "8 AI Cfg" → 配好 Key → 返回菜单 → 选 "7 AI" → **原问题已丢失**（§1.2 痛点）→ 重打 → 发送。
2. **配置 Key 时**：进入 Key 字段 → 明文显示 + 残影（§1.8 痛点）→ 输错末位 → Enter → **直接覆盖旧 Key**（§1.5 痛点）→ 退到对话屏 → 401 → 不知道刚才的 Key 是什么。
3. **配置模型时**：进入模型字段 → 没有历史（§1.7 痛点）→ 凭记忆输入 `gpt-4o` → 存盘 → 404 → 退到配置页 → 改成 `openai/gpt-4o`（OpenRouter 命名空间）→ 发送成功。
4. **发送成功翻页时**：800 字回答分 5 页 → 不知道在哪一页（§1.9 痛点）→ 逐页翻 → 想微调首句追问 → 翻回第一页 → 退出浏览 → 字符回输入态时把草稿覆盖了（§1.2 + §1.6 联动）。

这 4 条断点共同指向 §1.2（草稿）、§1.4（错误入口）、§1.5（保存确认）、§1.10（测试连接）四个高优先级 finding，修订建议按以下顺序推进：

| 顺序 | Finding | 影响范围 | 阻塞性 |
|---|---|---|---|
| 1 | §1.2 草稿保留 | 首次使用 + 日常使用 | 阻塞主流程 |
| 2 | §1.4 错误可执行入口 | 首次使用 + 任何失败恢复 | 阻塞主流程 |
| 3 | §1.3 取消语义 + §1.5 末字段二次确认 + §1.10 测试连接 | 配置体验 | 阻塞配置体验 |
| 4 | §1.1 当前生效配置可见 + §1.6 发送态切换语义 | 日常使用 | 不阻塞但显著影响 |
| 5 | §1.7 模型历史 + §1.8 Key 掩码 + 全刷 | 高频 / 隐私场景 | 不阻塞但显著影响 |
| 6 | §1.9 翻页页码 | 长回答场景 | 体验细节 |

> 建议完成顺序 1-3 之前不开始 `ui_ai_chat.cpp` / `ui_ai_cfg.cpp` 实质实现，否则会像 WiFi 配置屏那样经历多轮返工（参考 `docs/reviews/wifi-config-keyboard-review-result*.md` 系列）。
